01 /

First step: small task, clear result

Start with a task where you know if the answer makes sense. For example, by shortening your own text or comparing two supplied offers.

Give the AI background

Insert text, table or description of the situation. Write who the result is for and what should be preserved.

"Keep this email to five sentences. Keep the meeting date and the tone polite."

Determine the form of the result

Instead of "make it better somehow", describe what you want to get: a brief proposal, a list of questions or a table of differences.

"List the differences in price, terms and what is missing from the offer."

View the output

Check the names, numbers and meaning. If something doesn't fit, write a specific comment and have the part fixed.

"The transport is missing in the second point. Fill it in, leave the other points."

Why does the answer sometimes seem correct but not?

Flowing text by itself does not prove correctness. AI can fill in unsubstantiated data or misunderstand input. Ask her to separate the evidence from the assumptions. Then compare the important data with the original document or a reliable source.

A good assignment includes a goal, background, boundaries and verification method. No need for a long list of magic formulas.

Example: comparing accommodation

What does context mean and how to convey it?

Context is the context and background from which the AI is to be based. For text correction, it is the original wording and the target reader; when working with the code, related files and a description of the error. Add necessary information and remove unnecessary personal data. During longer work, continuously summarize what is already valid and what has changed.

03 /

Model, chat and working tool

These terms are often mixed up. The difference will help to understand why the same AI just answers somewhere and can edit the file elsewhere.

Model

Creates responses from the supplied input. The chosen model affects capabilities, speed and price.

Chat

An application in which you communicate with AI. Depending on the product and account, it may also offer files, search or other tools.

Agent

It works in repeated steps: it designs a procedure, uses an available tool, reads the result and continues.

Work environment

It determines which files, commands and services the AI can access and what permissions it has.

An example of a tool for working with a project is Claude Code. Always check the options of a specific product in its documentation.

04 /

From one answer to an AI agent

An achievable goal and a clear boundary are important for the agent. For example, prepare an overview of the accessible documents and save the proposal in the specified folder.

  1. Understand the goal
  2. Use the tool
  3. Check the result
  4. Continue or quit
An example of agent input and boundaries

"Go through these documents, prepare an overview of terms and cite the source for each. Save the result as a draft. Do not edit the documents or send messages to anyone."

A task has a specific output. Reading documents and preparing a proposal are different powers than deleting, sending or paying. Automate a repetitive task only after a single pass has been verified.

Will more agents always help?

Tasks can be broken down, but someone has to combine the results and resolve conflicts. With a little tweaking, one well-written task can become clearer. The division makes sense when the parts of the work are truly independent and their outputs can be verified.

05 /

Development by assignment: what comes after the first draft

With so-called vibe coding, you describe the desired behavior in ordinary language and AI helps prepare the code. It is important to be able to judge what the result really does.

Prototype

It will show the appearance and basic pass on test data. It will help to see if the idea is being used well.

Usable tool

It also needs data storage and recovery, error states, correct calculations, and reuse verification.

How to enter a small fix in an existing project

Describe how to trigger the error, what is happening and what should happen. Ask to find out the cause first. Then for a limited change and review of the same procedure. Consider the preview or test of the result separately from the AI's claim that it is done.

"On empty input, the form returns null as a valid result. Find the cause, correct this behavior only, and validate both the empty input and the normal value. Do not publish the change yet."

06 /

Versioning, Git and GitHub: an overview of every change

When editing, you need to know what has changed, why and to which verified state it can be returned. A history of changes, marked releases and a brief overview of what's new will help.

Application version

Release designation, for example 1.4.2. According to him, the user will recognize what form the application has. The changelog explains fixes, new functions and possible changes to working with data.

Git

Project File History Tool. It allows you to compare changes, save related modifications in a commit, and work in branches. He manages the basic work locally on the computer.

GitHub

A service for hosting repositories, collaboration and review of change proposals. It can run automatic checks or deployments if the project is set up to do so.

Glossary: commit, branch, push and pull request
Repository
The project and its versioned history.
Commit
Saved history point with change report. It arises from selected prepared changes; it does not capture unsaved work in the editor itself.
diff
Comparison of changes: what has been added, decreased or adjusted.
Branch and merge
A branch allows you to develop a change separately. Merge merges it into another branch; possible contradictions need to be resolved.
Push and pull
Push sends local history to a remote repository. Pull pulls and commits changes from the remote branch.
Pull request (PR)
Proposal to commit the change to GitHub. Allows you to go through the differences, comments, and results of pre-merge checks.

Git commands · GitHub — pull requests

What do the numbers 1.4.2 and the beta designation mean?

If the project uses semantic versioning (SemVer), the numbers have meaning according to public interface compatibility:

  • PATCHES: a patch to preserve compatibility, for example 1.4.2 → 1.4.3.
  • MINOR: a new backward compatible feature, for example 1.4.2 → 1.5.0.
  • MAJOR: incompatible public interface change, for example 1.4.2 → 2.0.0.

1.5.0-beta.1 indicates a preview version. Other designations of the "work" type have a meaning according to the rules of a specific project. Neither the version number nor the "final" label alone prove the correctness of the application.

SemVer rules in Czech

Save change, submit and publish

Commit saves selected changes to local history. Push sends them to a remote server. Deployment makes a certain version available to users.

A project can have deployment set automatically after a push or merge into the master branch. So before sending it, find out what it triggers. For example, GitHub Actions can perform builds, tests, and then releases.

GitHub — automated checks and deployments

How to prepare the possibility of return

Note a verified commit or tag a release, for example v1.4.2. A tag names a specific point in history; changelog describes the changes for users. Command git revert can create a new commit that reverses an earlier change and preserves history.

Backup the database, documents and user settings separately. Reverting to the old code may not return the data modified by the new version. For data format changes, prepare and verify the recovery procedure.

07 /

How to choose a model and not to overspend

Try the same task on your own materials. Track correctness, needed repairs, wait and price. The model name alone does not guarantee you the result.

What does effort mean — intensity of thinking?

For tools that offer this option, it is about setting the scope of the model's reasoning. A higher setting may help with a complex task, but is not a guarantee of correctness. Compare the result of the same input at different settings and calculate the time and consumption.

Official OpenAI documentation — model and reasoning effort

When is free enough and what does subscription mean?

Start with an available tool and a specific task. A paid tariff can make sense when you hit a limit or need a specific function. The conditions of the given product decide. Don't automatically consider a chat subscription to be paying for a separate API or hosting your own application.

Where to check the current model offer?

The offer in the chat and in the API may not be identical. Before making a decision, check the availability for your account, the price and any preview designation.

08 /

Skills, plugins and MCP made easy

Add-ons solve different needs: repeat a procedure, connect a service or make a tool available. Start with what you really need for your task.

Skill
Procedure for repetitive work, often with instructions and background. For example, how to prepare a report or verify a change. It does not retrain the model itself.
Plugins
A package that expands the application's capabilities. Depending on the environment, it can combine instructions, skills, tools and connections to services.
Connector
Linking to a service or account. Before connecting, find out what data it makes available and whether it also allows writing.
MCP server
It makes tools and data available through a common interface. It can run locally and remotely. The authority and credibility of the source still needs to be assessed.
An example of a difference in one task

You want to regularly prepare an overview of documents. A skill can describe the format and control of a report. The connector makes the folder available. The MCP server can provide the necessary tools. A plugin can package some of these capabilities together. The specific combination depends on the application.

09 /

What to never put in AI chat

Before you send a message, file or screenshot, check what it contains. These rules apply to regular conversation fields and attachments; login in the specified login or authorization window of the service.

Access secrets do not belong in chat

  • Passwords, PINs and login codes: as well as one-time SMS codes, backup codes and links to log in or renew your account.
  • API keys, tokens and private keys: for example, an AI service key, a GitHub access token, a private SSH key, or an active login cookie. Pay attention to the files as well .env and logos.
  • Crypto Wallet Recovery Phrase: Do not send seed phrase or private key to the chat, not even as a photo. Whoever gets them can control the wallet.
  • Payment data enabling card abuse: full card number, validity, CVV/CVC, PIN or confirmation codes for payment.

Other sensitive documents: delete data first and verify permissions

Documents and identity

Scan of ID or passport, birth number, signature, exact address, personal contacts or photos of children. Use fictitious or substituted data for a common query.

Health and privacy

Medical reports, intimate photographs, private communications and documents containing information about other people. Insert only the necessary extract stripped of identifying details.

Work and finance

Confidential contracts, payslips, statements, client lists and confidential company code. Do not upload them to a common public AI tool without permission; follow the rules of the employer.

Neither the paid plan nor the disabled use of training conversations in itself replaces the right to share third-party or confidential data. It depends on the specific service, settings and data rules.

How to prepare documents more safely
  1. Send only the part needed for the task. Replace the names, for example [KLIENT A], account number [ÚČET] and access data [ODSTRANĚNO].
  2. For the screenshot, check the top bar, page address, QR codes and side windows. Also consider comments, hidden sheets and metadata for the document.
  3. Remove sensitive data or use true blackout designed to remove content. By itself, a black rectangle over text in an editable document may not delete the original text.
  4. Review the resulting file and verify that the deleted content cannot be read or copied. Replacing the name may not be enough if other connections reveal the person.

ICO — hidden data and secure removal of document content.

Instead of the entire payslip: "Explain the difference between gross and net pay using a fictional example. I don't need to calculate the specific pay."

What if I've already submitted my password or key?

Do not consider the deletion of the message itself to secure the leaked access. Change the password directly in the original service; invalidate the published token or API key and replace it with a new one. Check logged in devices and account activity. For work data, inform the administrator, for payment card data, your bank. For the wallet recovery phrase, look for the provider's official security procedure.

10 /

API keys: how to work with them securely

The API key allows the application to access the service. Misuse of the secret key may result in third-party requests being charged to your account. The following procedure applies to secret keys for server APIs, such as AI services.

1. Create it at the provider

Use official account management. Separate development and live operation and set only necessary permissions. Use expiration and access restrictions if the service offers them.

2. Save it outside the code

For local development, use an environment variable; hosting secret settings or secret manager in operation. Do not add the key to the chat, documentation, screenshot or log.

3. Use it on the server

The browser sends a request to your server. The server calls the API with the key and returns a response. The secret key is not sent to the visitor.

You cannot hide the secret key on the public page

Do not put it in HTML, JavaScript for the browser, or in localStorage. Variables like VITE_… or NEXT_PUBLIC_… they can be part of a public build. Even hiding or encoding a value does not make it a secret. See · Next.js.

The server endpoint also needs its own access control, request throttling, and input control so that anyone can't use it indefinitely at your expense.

Example: retrieving a key without listing it

Create a variable in the server or development environment settings AI_API_KEY. Put its actual value there, not in the source code. This server-side Python example does not call any APIs:

import os

api_key = os.environ["AI_API_KEY"]
print("Proměnná s klíčem je načtená.")
# Hodnotu api_key nevypisuj.

The name of the variable depends on the application. Some libraries expect a custom name, for example OPENAI_API_KEY. File .env is not loaded automatically in every environment and does not provide encryption by itself.

How to prevent your key from being submitted to GitHub

Local file with secrets include in .gitignore. Shared demo .env.example should contain only variable names and empty or obviously invalid values. Check the changes before committing; checking for secret leaks can help.

Adding to .gitignore will not remove a key that has already been committed. A private repository is also not a secret keeper.

Consumption and limits: what to watch

Continuously check traffic and costs in the provider's account. Separate projects and keys will help track consumption. Budget alerts may not automatically stop requests; the actual limit and its method of applying verifications in the given service.

Key leakage: correct order of remedy
  1. Invalidate the leaked key immediately with the provider. It is not enough to delete it from the message or from the latest version of the file.
  2. Create a spare key, update the application settings and verify its operation.
  3. View usage history, costs, and related accesses. Discuss suspicious activity with the provider.
  4. Remove the leak. If the secret is in Git's history, cleanup according to the documentation and in agreement with others; copies can remain in both clones and forks.

11 /

Application review after modification and regression

A regression is a bug where something that used to work stops working after a new modification. Therefore, a fixed button does not mean that the entire application is verified.

Before the change

Note the version and original behavior. For the error, write down the invocation procedure and the expected result. Verify the default status of relevant tests and protect the data you will be working with.

After the change

Repeat the original procedure and verify the repair. Then go through the following functions: saving, loading, calculations or exporting depending on where the change affects.

Before and after release

Review the changed files and verify the build as well as the local preview. After approved deployment, try the main passages also in the actually released application.

What to test: individual layers of control
  • Syntax and assembly: code can be processed and applications can be built. This has not yet verified its result.
  • Unit tests: selected calculations or rules on known inputs.
  • Integration tests: cooperation of parts, for example import and save.
  • User pass: actually entering values, clicking, saving and reloading.
  • Visual inspection: mobile and computer, longer text, error message and readability of controls. Comparing the screenshots can highlight a change in appearance.

Adapt the scope to the change and its effects. A text correction needs a different check than an accounting calculation or database change.

A specific regression example: fixing an import

Imagine an application to prevent the repeated import of the same items. Correcting the new listing format must also maintain this rule.

  1. On the test data, import three different movements and verify three items.
  2. Try the same file a second time. Three entries must still remain if the application is to recognize duplicates.
  3. Check totals, currencies and date. Also try a previously supported format.
  4. Save the data, open the application again and verify the export.

Use test or anonymized data. After finding a bug, it's a good idea to add a test that verifies the expected behavior and helps catch its return.

Smoke test, regression test and CI made easy

Smoke test is a quick verification of the basic passes: the application starts, the main page loads, and the key task can be performed.

Regression tests they monitor the previously requested behavior for further changes. CI means continuous integration: automated checks can run, for example, when a pull request is created. The green result shows only checks that actually started.

How to enter an AI check and what to want in the result

"First, find out and record the default state. After fixing, verify the original bug and related functionality. Use test data. List what you checked, what the expected and actual result was, and what failed to verify. Don't publish anything yet."

Demand specific results and open deficiencies. The number of successful tests or the sentence "everything works" alone is not a substitute for checking important user scenarios.

What if the check finds an error?

Record the progress, version and expected result. Find out if the problem existed before the modification. Depending on the impact, correct the change or use a prepared return; go through the affected scenarios again after the fix. Don't overwrite reference screenshots or expected results just to pass the check.
