How an idea becomes a working change

I start with a need from everyday use. For a bug I first want to understand the cause; for a feature I define the behavior and scope.

  1. 01

    Brief

    Describe the goal, evidence and expected behavior, including the project's rules.

  2. 02

    Current state

    AI reads the code and documentation. We separate evidence from assumptions.

  3. 03

    Change

    Build on the existing solution. The change has a clear scope and can be reviewed.

  4. 04

    Verification

    Use relevant tests, reproduce bugs and explore the interface. The original failure must disappear.

  5. 05

    Use and iterate

    I assess the result in practice. Bugs, logs and feedback inform the next task.

What AI does and what I decide

AI helps carry out the work

  • Reads provided evidence and finds inconsistencies.
  • Proposes solutions and edits code and text.
  • Runs relevant checks and summarizes the result.

I set the direction

  • Define the need, priorities and scope.
  • Decide whether the result works well in practice.
  • Approve publication and operational changes according to the task.

A local app and a cloud AI model are different things. Recognizing a photo through Gemini, for example, involves sending that selected photo to an external service. What I provide to AI matters.

07 /

An app in an evening? A demo is not a finished product.

AI can quickly create a screen, form or chart. “No manual coding” does not mean “no work, understanding or responsibility”. A short demonstration does not prove that the whole application is reliable.

What a quick prototype does

Shows the idea, design and a basic flow with sample data. Useful for choosing a direction, not automatically suitable for real financial records.

What a real application must do

Handle correct calculations, failures, repeated imports, storage, updates and restoring backups. Verification continues during everyday use.

In finance, the numbers must work—not just the design.

PT and Účetní kniha need checks for fees, currencies, rounding and the meaning of returns. Transfers between my own accounts must not create false income. Importing the same statement twice must not duplicate transactions. A backup matters only if I can restore the data.

AI helps produce the code. Tests and checked results must establish correctness—not the model saying “done”.

How to assess courses and easy-development promises

A paid course or Discord can provide structure and support. I look for debugging, version control, security and testing, not just a first successful demonstration. Video duration is not the time required to finish my project.

AI is not an automatic shortcut to understanding: an Anthropic experiment highlights the importance of actively asking for explanations and learning with AI. This is not a universal verdict against AI. Anthropic research

09 /

Is free AI enough? It depends on the work.

Free does not automatically mean poor, and paid does not mean correct. Differences often concern available models, usage capacity and tools—not just one answer’s quality.

Free: a useful starting point

Concept explanations, translations, short texts, ideas and small prototypes. A capable model may be available with lower limits. If I can finish the task and verify it, a “Pro” label alone is no reason to pay.

Paid: room for sustained work

May be useful for regular development, long analyses and many correction cycles. Depending on the plan, it adds higher limits, more models or development tools. A subscription does not generally mean unlimited usage.

A chat subscription ≠ running AI in my application

An AI analyst or photo recognition through an API has its own terms and billing. Do not assume a subscription pays for API calls; some plans may include credits. Hosting, storage and other data services may cost extra.

Try my actual task first. Pay for a needed capability or a specific limit—not a promise of perfect answers.

Prices, availability and limits vary by product, region and account. Current terms: OpenAI · Claude · Gemini · Gemini API. Payment alone does not guarantee privacy; I check the specific terms before providing sensitive data.

10 /

Skills, plugins and MCP: workflows and access

These components can simplify work, but each serves a different purpose. A first application does not need every integration.

Skill
Instructions for repeatable work, optionally with scripts and references. For example, checking imports or running tests. Not additional model training.
Plugin
An installable capability package. May contain skills, tools and MCP connections. Its origin and contents matter.
Connector
A connection to a service or account. Before connecting, I check which data it exposes and whether it can also write.
MCP server
Exposes tools and data through a common interface. Can run locally or remotely. MCP is not a security certificate.

My practical approach: choose a trusted source, read instructions, grant the minimum permissions and try a concrete task with test data. Separate writing, deleting and publishing from reading. More add-ons do not automatically improve results. Plugin documentation · MCP security
