01 /

First step: a small task with a clear result

Start with a task where you can judge whether the answer makes sense, such as shortening your own text or comparing two offers you provide.

Give AI the source material

Provide the text, table or situation. Explain who the result is for and what must stay unchanged.

“Shorten this email to five sentences. Keep the meeting date and a polite tone.”

Specify the output

Instead of “make it better”, say what you want: a short proposal, a list of questions or a comparison table.

“List the differences in price, terms and anything missing from the offer.”

Review the result

Check names, numbers and meaning. If something is wrong, give specific feedback and ask for that part to be corrected.

“Point two is missing transport. Add it and leave the other points unchanged.”

Why can an answer sound right and still be wrong?

Fluent writing does not prove accuracy. AI may invent a detail or misunderstand the request. Ask it to separate supported information from assumptions. Check important facts against the original material or a reliable source.

02 /

A request you can verify

A good request includes the goal, source material, boundaries and a way to check the result. You do not need a long list of magic phrases.

Example: comparing accommodation

Paste two real offers into the template. AI should use their contents and point out missing terms.

Before booking, check the price and availability directly with the provider. This example shows how to work with source material; it does not place a booking.

Compare these two accommodation offers for two people for three nights. Use only information from the supplied material. In a table, list the total price, location, breakfast, parking and cancellation terms. Mark missing information as “not established”. Finish with three questions I should ask before booking. Do not book or pay for anything. Offer A: [paste text] Offer B: [paste text]
What is context and how do you provide it?

Context is the background and source material AI should use. For editing text, provide the original wording and intended reader; for code, the related files and a description of the bug. Include relevant information and remove unnecessary personal details. During longer work, regularly summarise what is still valid and what has changed.

03 /

Models, chats and working tools

These terms are often mixed up. The distinction explains why the same AI can only answer in one setting but edit a file in another.

Model

Generates answers from the supplied input. The model affects capability, speed and cost.

Chat

The application where you communicate with AI. Depending on the product and account, it may also offer files, search or other tools.

Agent

Works in repeated steps: proposes an approach, uses an available tool, reads the result and continues.

Working environment

Determines which files, commands and services AI can access and what permissions it has.

One example of a tool for working on a project is Claude Code. Always check the specific product’s capabilities in its documentation.

04 /

From a single answer to an AI agent

An agent needs an achievable goal and clear boundaries. For example, summarise the documents it can access and save a draft in a specified folder.

  1. Understand the goal
  2. Use a tool
  3. Check the result
  4. Continue or finish
Example: an agent’s task and boundaries

“Review these documents, list the deadlines and cite the source for each one. Save the result as a draft. Do not edit the documents or send messages to anyone.”

The task has a specific output. Reading material and preparing a draft require different permissions from deleting, sending or paying. Automate a repeated task only after verifying one complete run.

Do more agents always help?

Tasks can be split, but someone must combine the results and resolve disagreements. For a small change, one clearly defined task may be easier to follow. Splitting work makes sense when the parts are genuinely independent and their outputs can be checked.

05 /

Developing through requests: after the first draft

In so-called vibe coding, you describe the desired behaviour in ordinary language and AI helps prepare the code. You need to be able to judge what the result actually does.

Prototype

Shows the appearance and a basic flow using test data. Helps assess whether the idea is usable.

A usable tool

Also needs data storage and recovery, error handling, correct calculations and checks of repeated use.

How to request a small fix in an existing project

Describe how to reproduce the bug, what happens and what should happen. First ask for the cause to be identified, then for a limited change and a check of the same steps. Judge the preview or test separately from AI’s claim that the work is done.

“When the input is empty, the form displays zero as a valid result. Find the cause, fix only this behaviour and check both empty input and a normal value. Do not publish the change yet.”

06 /

Versioning, Git and GitHub: track every change

When making changes, you need to know what changed, why, and which verified state you can return to. A history, labelled releases and a short changelog help.

Application version

A release label, such as 1.4.2. It tells users which edition they have. A changelog explains fixes, new features and any changes to data handling.

Git

A tool for tracking project files. It compares changes, records related edits in commits and supports branches. Basic work happens locally on your computer.

GitHub

A service for hosting repositories, collaboration and reviewing proposed changes. It can run automated checks or deployments if the project is configured to do so.

Glossary: commits, branches, push and pull requests
Repository
The project and its versioned history.
Commit
A recorded point in history with a message describing the change. It records selected, staged changes; it does not capture unsaved work in your editor.
Diff
A comparison showing what was added, removed or changed.
Branch and merge
A branch lets you develop a change separately. A merge incorporates it into another branch; any conflicts must be resolved.
Push and pull
Push sends local history to a remote repository. Pull downloads and integrates changes from a remote branch.
Pull request (PR)
A proposal to incorporate changes on GitHub. It lets reviewers examine differences, comments and check results before merging.

Git commands · GitHub — pull requests

What do 1.4.2 and beta mean?

If a project uses Semantic Versioning (SemVer), the numbers describe compatibility of the public interface:

  • PATCH: a compatible fix, for example 1.4.2 → 1.4.3.
  • MINOR: a new backward-compatible feature, for example 1.4.2 → 1.5.0.
  • MAJOR: an incompatible public-interface change, for example 1.4.2 → 2.0.0.

1.5.0-beta.1 denotes a prerelease. Labels such as “work” depend on the project’s own rules. Neither a version number nor the label “final” proves that an application is correct.

SemVer specification

Saving, uploading and publishing a change

Commit records selected changes in local history.Push sends them to a remote server.Deployment makes a particular version available to users.

A project may deploy automatically after a push or merge into the main branch. Before sending changes, find out what will run. GitHub Actions can, for example, build, test and then publish a release.

GitHub — automated checks and deployments

How to prepare a way back

Record a verified commit or mark a release with a tag, for example v1.4.2. A tag names a point in history; the changelog describes changes for users. The command git revert can create a new commit that reverses an earlier change while preserving history.

Back up the database, documents and user settings separately. Returning to old code may not restore data changed by a new version. For data-format changes, prepare and test a recovery procedure.

07 /

Choosing a model without overspending

Try the same task using your own material. Compare accuracy, corrections needed, waiting time and cost. A model’s name alone does not guarantee a result.

What does reasoning effort mean?

In tools offering this option, it adjusts the model’s reasoning effort. A higher setting may help with a complex task but does not guarantee accuracy. Compare the same request at different settings, accounting for time and usage.

Official OpenAI documentation — models and reasoning effort

When is free enough, and what does a subscription cover?

Start with an available tool and a specific task. A paid plan may make sense when you hit a limit or need a particular feature. The product’s terms matter. A chat subscription does not automatically pay for a separate API or hosting your application.

OpenAI · Claude · Gemini API

Where can you check the current model selection?

The chat and API may not offer the same models. Check availability for your account, pricing and any preview designation before deciding.

08 /

Skills, plugins and MCP explained

Extensions meet different needs: repeating a workflow, connecting a service or providing a tool. Start with what your task actually requires.

Skill
A workflow for repeated work, often with instructions and source material. For example, how to prepare a report or verify a change. It does not retrain the model by itself.
Plugin
A package extending an application. Depending on the environment, it can combine instructions, skills, tools and service connections.
Connector
A connection to a service or account. Before connecting, check which data it exposes and whether it also allows writing.
MCP server
Exposes tools and data through a shared interface. It can run locally or remotely. You still need to assess permissions and the source’s trustworthiness.
The difference in one example

Suppose you want regular summaries of documents. A skill can describe the report format and checks. A connector provides folder access. An MCP server can supply the tools. A plugin may bundle some of these capabilities. The combination depends on the application.

09 /

What never to put in an AI chat

Before sending a message, file or screenshot, check its contents. These rules apply to ordinary chat fields and attachments; sign in through the service’s designated login or authorisation window.

Access secrets do not belong in chat

  • Passwords, PINs and login codes: including one-time SMS codes, recovery codes and links that can sign you in or restore access to an account.
  • API keys, tokens and private keys: for example, an AI-service key, GitHub access token, private SSH key or active login cookie. Also check files such as .env and logs.
  • Crypto-wallet recovery phrases: never send a seed phrase or private key to chat, even as a photo. Anyone who obtains them can control the wallet.
  • Payment details that could enable card misuse: full card number, expiry date, CVV/CVC, PIN or payment confirmation codes.

Other sensitive material: remove details and check permission first

Documents and identity

ID or passport scans, national identification numbers, signatures, exact addresses, personal contacts or photos of children. For ordinary questions, use fictional or substituted details.

Health and privacy

Medical reports, intimate photos, private messages and documents containing other people’s data. Include only a necessary excerpt with identifying details removed.

Work and finance

Non-public contracts, payslips, statements, client lists and confidential company code. Do not upload these to an ordinary public AI tool without permission; follow your employer’s rules.

A paid plan or disabling the use of chats for training does not grant permission to share other people’s data or confidential information. It depends on the service, its settings and the rules applying to the data.

How to prepare safer source material
  1. Send only what the task needs. Replace names with, for example, [CLIENT A], account numbers with [ACCOUNT] and access credentials with [REMOVED].
  2. Check the screenshot’s top bar, URL, QR codes and nearby windows too. In documents, consider comments, hidden sheets and metadata.
  3. Remove sensitive details or use proper redaction that deletes the content. A black rectangle placed over text in an editable document may leave the original text intact.
  4. Inspect the resulting file and check that removed content cannot be read or copied. Replacing a name may not be enough if other details identify the person.

ICO — hidden data and safe document redaction.

Instead of a full payslip: “Explain gross versus net pay using a fictional example. I do not need a calculation of my actual salary.”

What if I have already sent a password or key?

Deleting the message alone does not secure leaked access. Change the password directly in the original service; revoke an exposed token or API key and replace it. Check signed-in devices and account activity. For work data, inform your administrator; for card details, contact your bank. For a wallet recovery phrase, follow the provider’s official security procedure.

10 /

API keys: how to handle them safely

An API key lets an application access a service. Misuse of a secret key can mean someone else’s requests are charged to your account. This guidance concerns secret server-side API keys, for example for AI services.

1. Create it with the provider

Use the official account dashboard. Separate development from production and grant only the permissions needed. Use expiry and access restrictions if offered.

2. Store it outside the code

For local development, use an environment variable; in production, use hosting secrets or a secrets manager. Do not place the key in chat, documentation, screenshots or logs.

3. Use it on the server

The browser sends a request to your server. The server calls the API with the key and returns the response. The visitor never receives the secret key.

A public page cannot keep a secret key

Do not put it in HTML, browser JavaScript or localStorage. Variables such as VITE_… or NEXT_PUBLIC_… may be included in the public build. Hiding or encoding a value does not make it secret. Vite · Next.js.

The server endpoint also needs access controls, request limits and input validation, so that anyone cannot use it without limits at your expense.

Example: load a key without printing it

In the server or development environment settings, create a variable named AI_API_KEY. Enter its actual value there, not in the source code. This server-side Python example makes no API calls:

import os

api_key = os.environ["AI_API_KEY"]
print("The key environment variable has been loaded.")
# Do not print the value of api_key.

The variable name depends on the application. Some libraries expect a specific name, for example OPENAI_API_KEY. A .env file is not automatically loaded in every environment and does not provide encryption by itself.

How to prevent uploading a key to GitHub

Include local secrets files in .gitignore. A shared .env.example should contain only variable names and empty or obviously invalid values. Review changes before committing; secret scanning can help.

Adding a file to .gitignore does not remove a key that has already been committed. A private repository is not a secrets manager either.

Usage and limits: what to monitor

Regularly review usage and costs in the provider’s dashboard. Separate projects and keys help trace spending. A budget alert may not stop requests automatically; check the actual limit and how the service enforces it.

A leaked key: the order of recovery
  1. Immediately revoke the leaked key with the provider. Deleting it from a message or the latest file version is not enough.
  2. Create a replacement key, update the application settings and verify that it works.
  3. Review usage history, costs and related access. Contact the provider about suspicious activity.
  4. Remove the source of the leak. If the secret is in Git history, follow the cleanup documentation and coordinate with others; copies may remain in clones and forks.

11 /

Checking an application after changes and regression testing

A regression is a bug where a new change breaks something that used to work. Fixing one button therefore does not mean the whole application has been verified.

Before the change

Record the version and original behaviour. For a bug, note the reproduction steps and expected result. Establish the relevant tests’ baseline and protect any data you will use.

After the change

Repeat the original steps and verify the fix. Then check related functions: saving, loading, calculations or export, depending on the change’s scope.

Before and after release

Review the changed files and verify the build and local preview. After an approved deployment, check the main user flows in the version actually released too.

What to test: the layers of verification
  • Syntax and build: the code can be processed and the application built. This does not yet verify the result.
  • Unit tests: selected calculations or rules using known inputs.
  • Integration tests: interaction between components, such as importing and saving.
  • User flow: actually entering values, clicking, saving and reloading.
  • Visual checks: mobile and desktop, longer text, error messages and readable controls. Screenshot comparisons can reveal visual changes.

Match the scope of checks to the change and its impact. A text correction needs different checks from a change to accounting calculations or a database.

Regression example: fixing an import

Imagine an application that must prevent importing the same items twice. Adding support for a new statement format must preserve that rule.

  1. Using test data, import three different transactions and verify that there are three records.
  2. Try the same file again. If the application must detect duplicates, the total must still be three records.
  3. Check totals, currencies and dates. Also try a previously supported format.
  4. Save the data, reopen the application and check the export.

Use test or anonymised data. After finding a bug, add a test of the expected behaviour to help catch its return.

Smoke tests, regression tests and CI explained

Smoke test is a quick check of basic flows: the app starts, its main page loads and the key task can be completed.

Regression tests guard previously required behaviour during later changes. CI means continuous integration: automated checks can run, for example, when a pull request is created. A green result proves only the checks that actually ran.

How to ask AI to check work and report results

“First establish and record the baseline. After the fix, check both the original bug and related functions. Use test data. State what you checked, the expected and actual results and anything you could not verify. Do not publish anything yet.”

Ask for specific results and unresolved issues. A count of passing tests or “everything works” does not replace checking important user scenarios.

What if a check finds a bug?

Record the steps, version and expected result. Establish whether the issue existed before the change. Depending on its impact, fix the change or use the prepared rollback; then recheck affected scenarios. Do not overwrite reference screenshots or expected results merely to make a check pass.
