Overview of household consumption

I want to see when and where the household consumes electricity. On this page, I distinguish between direct measurements and estimates based on operating time and show how I record the data.

Technical details

Runtime-based kWh estimate boilers, plug devices with power metering, rolling daily and yearly tracking. From May 12, 2026 plus Shelly Pro 3EM in the switchboard — three current coils on three phases measure real consumption every 30 seconds. Finally, hard numbers instead of estimates.

What does it do?

Measuring where it works, estimating where it doesn't

The main appliance is an electric boiler 9 kW Protherm RAY. There is no real meter yet — instead the runtime is calculated: every 2 minutes demand cron increments the counter when the boiler is on. At the end of the day, it adds up kwh = (runtime_today_s / 3600) × kotel_kw. About 95% accuracy, because the boiler internally modulates 3 / 6 / 9 kW according to the water temperature.

Plug devices (sockets with Z-wave power metering) measure directly — in addition to on/off, they have capabilities measure_power in watts. Current consumption is sampled into EventLog and daily integration gives kWh. Some sockets have i meter_power (cumulative counter, makes measurement more accurate through restarts).

The goal is not absolute invoice-grade accuracy — the goal is to know which appliance eats how much and when. From this it can be deduced that the boiler consumes ~3,500 kWh per year, the refrigerator needs ~250, the idle computer ~80, the rest negligible. The real billing measurement runs in parallel via Shelly Pro 3EM (CT clamps for 3 phases in the switchboard, live from 12/05/2026).

Daily operation

How it is measured during the day

Continuous sampling, daily aggregation, rolling history.

  1. Continuous

    Sample every 2 min

    sh_heating_demand_v1 cron: if boiler_state='on', runtime_today_s += 120. Plug devices measure capabilities measure_power in real-time, they are sampled passively.

  2. 00:00

    Daily reset

    Midnight → runtime_yesterday_s = runtime_today_s a runtime_today_s = 0. Yesterday's value is used for briefing ("Yesterday boiler X min, about Y kWh"). Reset_date track is written for audit trail.

  3. Weekly

    Trend aggregation

    The weekly average is calculated from 7 yesterday's values. It is used to detect anomalies (the boiler ran 50% longer than average → something is wrong with the insulation? open windows? a bug in the scheduler?).

  4. Yearly

    Cumulative total

    runtime_total_s never reset — a cumulative counter for the lifetime of the script. From this, you can derive the life-cycle consumption of the boiler, predict when it will require service, etc.

Scenes

Five situations where measurement is useful

Some are dashboard-driven, others automatic alerts.

Dashboard tiles

Heating page has kWh today + runtime today. Realtime value read directly from variables. Yesterday's value for comparison. Weekly average as sparkline.

Briefing mention

When yesterday ≥ 0.5 kWh, the phase 2 briefing mentions: "Yesterday boiler X min, about Y kWh". Specific dates in morning talk, no "maybe a lot" guesses.

Anomaly alert

Brain Guardian: if runtime on one day > 200% of weekly average, alert to EventLog. Suggested checks: open windows, scheduler bug, anti-cycling guard issue.

Plug power log

It is sampled every 5 min measure_power of all plug devices to EventLog. From this, a daily curve is constructed — when the PC was turned on / off, when cooking was done, when the washing machine was running.

Yearly review

Cumulative total per device → annual overview. Plan: GitHub Actions cron 1.1. generates the annual report .md to the rep, automatically pushes. The manual then compares with previous years.

Hardware

What does it actually measure?

Plug-level metering where it makes sense, runtime estimate where there is no choice.

13× Plug devices

Z-wave / Wi-Fi · power + meter

Sockets with capability measure_power (real-time W) a meter_power (cumulative kWh). Used on: PC, refrigerator, monitor, audio system, charger, etc. Cheap way to measure one appliance.

Fibaro FGS-214 (boiler)

Z-wave switch · runtime tracking

Main switch for the boiler. It does not have power metering itself (only on/off + status), therefore runtime-based estimate. Live Shelly Pro 3EM (from 12/05/2026) supplements the runtime estimate with real per-phase measurements for cross-check.

3× Fibaro FGT-001 (TRV)

Thermal head · battery powered

It does not have power metering for the heating circuit — it only measures itself (battery level). Useful as secondary data — when the TRV valve is closed but the boiler is running, something is disconnected. Tracking via runtime + comparison.

FGS-223 (Reserve)

Double Switch 2 · power metering · unmapped

Z-wave switch with native power metering capability. Not currently connected — a candidate for a heating circulation pump (heating Phase C+) or a boiler. Up to physical installation, new metric stream for energy tracking.

Shelly Pro 3EM LIVE

3 CT clamps · 3-phase · Wi-Fi · IP 192.168.1.xxx

Installed on May 12 in the cabinet. Three current coils per 3 phases measure consumption (W) and direction (take/produce) in real time, plus calculate total kilowatt hours per phase. The RPi asks it every 30 seconds with an HTTP request and stores 17 values ​​in Homey as variables — per-phase V/A/W, total, consumed and returned energy, board temperature.

During installation, it showed a slight export of −8.8 W (slightly giving something to the network, maybe solar or CT clamp reversed) — that will need to be verified or fine-tuned. Otherwise, it is finally a hard source of the truth about consumption, which complements the boiler's runtime estimate and per-plug measurements.

Shelly Plus PM Mini Gen3 LIVE

2× plug power meter · Wi-Fi

Two new meter sockets added in May — one for the coffee maker in the kitchen, the other for the stove. They added the list of 11 existing plug-meters to 13. Small, cheap (~470 CZK/piece), Matter-ready via Wi-Fi.

For the tech-savvy

What's going on under the hood

Runtime tracking, plug sampling, HA Energy Dashboard planned.

Runtime → kWh formula 
// In sh_heating_demand_v1 (cron 2 min)
if (boiler_state === 'on') {
  runtime_today_s += 120;  // = sample interval
}

// kWh estimate
kwh_today = (runtime_today_s / 3600) * kotel_kw;
// kotel_kw = 9 (configured per device)

Source of inaccuracy:

  • The boiler modulates 3 / 6 / 9 kW according to the water temperature — the estimate uses a maximum of 9 kW
  • Sample interval 2 min — error ±60 s on on/off transition
  • Boiler_state recorded up to 1-2 s after physical transition (Z-wave latency)

Net effect: estimate slightly overestimates (~95%). Not enough for invoicing, enough for trend analysis.

Plug power sampling

sh_plug_sampler_v1 cron 5 min iterates 11 plug devices, reads measure_power capability and writes to the EventLog with a timestamp. History is constructed from this:

  • Real-time: current W per plug
  • Daily integral: ∫(W) dt = daily kWh
  • Capability meter_power: cumulative counter, refines over restarts

Devices they don't have measure_power (only on/off) are ignored — runtime tracking is not worth it for them.

HA Energy Dashboard (planned)

todo_homeassistant_rpi_integration.md — phase 5 of the plan. Home Assistant on RPi4 as a read-only observer for 11 plug devices. Energy Dashboard will give a per-device + total view.

Pipeline: Homey → MQTT → HA → Energy Dashboard. Integration via HACS Homey add-on (if available), otherwise custom MQTT bridge. User pending: Long-Lived Token + Terminal & SSH add-on.

Yearly aggregation (GitHub Actions cron)

Plan for 1.1.: GitHub Actions cron download EventLog annual export, calculate per-device kWh totals, generate reports/yearly_<rok>.md and auto-push to the smart-home-website rep. Read-only output for the web (Phase D — case studies like "Year of heating").

Implementation does not depend on Homey — GitHub Action pulls EventLog from SSD JSONL on HA RPi (as of 5/27/2026; previously via Google Sheets API) + processes openpyxl / pandas + commit.

Anomaly detection (runtime > 200% avg)

Brain Guardian invariant: if daily runtime > 200% rolling 7-day average, alert. Possible causes:

  • Open window (heating loss) — door/window sensor should detect
  • Scheduler bug (target_temp stuck on top)
  • Anti-cycling guard does not work (cooldown bug 25.4. resolved)
  • TRV valve mechanically stuck (battery battery? can't close?)
  • Seasonal change (extra cold weeks) — false positive

Alert is a read-only flag, no auto-actions. The user must verify and decide.
