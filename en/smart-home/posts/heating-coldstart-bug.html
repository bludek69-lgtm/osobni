Cold-start anti-cycling bug — boiler stuck forever

Heating Phase A went live on the morning of 4/21. The boiler turned on, ran for 5 minutes, turned off. Then he never closed again. EventLog reported every 2 minutes hold_off_180s_left, where 180 it was counted from time-since-last-on and did not scroll down.

The anti-cycling guard was insured against rapid switching of the boiler (contactor protection). It basically worked, but had an edge case on cold start — where min_offtime_s never expired. Here are 4 hours of diagnostics.

Symptom

The boiler switched on once, heated the bathroom to the target temperature (approx. 5 min), then switched off according to hysteresis. Here's the end-of-story — from that point on, it never turned on again, even when the temperature dropped far below the target.

EventLog from demand cron every 2 min: 

06:14:00 demand=on  jidelna=21.0/21.0  koupelna=22.1/22.0  → boiler_request=on
06:16:00 demand=on  ...                                  → boiler_request=on
06:21:00 demand=off jidelna=21.0/21.0  koupelna=22.0/22.0 → boiler_request=off
06:23:00 demand=on  jidelna=20.4/21.0                    → hold_off_180s_left=180
06:25:00 demand=on  jidelna=20.3/21.0                    → hold_off_180s_left=180
06:27:00 demand=on  jidelna=20.2/21.0                    → hold_off_180s_left=180
... (forever)

hold_off_180s_left the count down did not continue. The boiler forever held off, the dining room slowly dropped to 21 → 20 → 19 → 18 °C. Without intervention, it would drop to anti-freeze 7 °C (where the safety bypass would force the boiler to shut down).

Anti-cycling guard logic

sh_heating_demand_v1 v1.1 had this check: 

// v1.1
const sinceTs = parseInt(await getVar('sh_heating_boiler_since_ts'), 10);
const elapsed = Math.floor((Date.now() - sinceTs) / 1000);
const minOfftimeS = parseInt(await getVar('sh_cfg_heating_min_offtime_s'), 10);

if (boilerState === 'off' && elapsed < minOfftimeS) {
  return {
    request: 'off',
    reason: `hold_off_${minOfftimeS - elapsed}s_left`
  };
}

The logic was: if the boiler is off and less than has passed since the last off min_offtime_s (default 180 s = 3 min), keep it off to protect the contactor.

Edge case — cold start

sh_heating_boiler_since_ts was on a fresh install of the script not registered / undefined. parseInt(undefined) = NaN. Date.now() - NaN = NaN. Math.floor(NaN / 1000) = NaN.

And now the key moment: NaN < 180 in JavaScript will evaluate false. So during the first 5 min of running (when the boiler first switched on) there was an else branch and everything worked.

But after the first off transition (the boiler turns off according to hysteresis) it registered since_ts = 0 some shadow logic (debug log revealed — one execution path did not set since_ts correctly when off transition, and default value was 0 from initialization). 

// since_ts = 0
elapsed = Math.floor((1697123456000 - 0) / 1000)
       = 1697123456
// 1697123456 < 180 ? FALSE!
// Wait, that's not the bug...

Hmm. 1697123456 < 180 is false, so the guard would NOT FAIL. The script should continue normally.

The real root cause

After another debug log, I found out that there was no problem elapsed < minOfftimeS, but another piece of code below: 

// Safety cutoff
if (sinceTs > 0) {
  // Validation runtime checks
  ...
}

// Anti-cycling check (the actual guard)
if (boilerState === 'off') {
  const safeElapsed = sinceTs > 0 ? elapsed : 0;
  if (safeElapsed < minOfftimeS) {
    return {request: 'off', reason: `hold_off_${minOfftimeS - safeElapsed}s_left`};
  }
}

Here is defensive coding — if sinceTs was 0 or negative (error in init), use safeElapsed=0 → fall through to guard. 0 < 180 = true → guard closes → return hold_off.

The logic should have been: "if sinceTs does not apply, let the boiler close (skip guard)". Instead: "if sinceTs does not apply, treat as right-now (most conservative) → guard always blocks".

Fix v1.2

// v1.2 — explicit cold-start escape
if (boilerState === 'off') {
  const safeElapsed = sinceTs > 0
    ? elapsed
    : Number.MAX_SAFE_INTEGER;  // ← cold start: bypass guard
  if (safeElapsed < minOfftimeS) {
    return {request: 'off', reason: `hold_off_${minOfftimeS - safeElapsed}s_left`};
  }
}

Key change: sinceTs > 0 ? elapsed : Number.MAX_SAFE_INTEGER. Cold start = pretend infinite time elapsed → guard never blocks.

Plus fixed everywhere else in the code (3 more places) where sinceTs > 0 check was used as a gate with incorrect default behavior.

Test

Reset all heating state vars (cold start simulation), run demand cron manually: 

06:30:00 (cold start) demand=on jidelna=18.0/21.0 → boiler_request=on
06:30:00 since_ts=<set>
06:32:00 demand=on  jidelna=18.5/21.0 → boiler_request=on (still cold)
...
06:45:00 demand=off jidelna=21.0/21.0 → boiler_request=off (target reached)
06:45:00 since_ts=<updated to off transition>
06:47:00 demand=on  jidelna=20.4/21.0 → hold_off_60s_left (legitimately cooling down)
06:48:00 demand=on  jidelna=20.3/21.0 → boiler_request=on (180s elapsed)

Test passed. Cold start not recognized as an anti-cycling violation, normal cycling behaves normally after the first off.

What was learned

"Default safe" is often not default safe. Defensive coding that assumes the worst-case can add its own bug class — a guard that "prefers to block rather than release" can lead to system paralysis.

Lessons from this bug:

  • Edge case 0 / undefined / NaN. Always explicit handling, not implicit fallthrough via JS coercion. NaN < 180 = false is a gotcha I ran into.
  • Cold start = safety bypass. At a cold start, guards have by definition "lack of data" — the default behavior should be "let through on first run", not "block all".
  • Orthogonality safety cap. Another safety guard (max_runtime_s 4h forced off) would not help here — the boiler was off, not him. Layered safeguards need to cover all paths, not just the on-path.
  • EventLog is my best friend. Without detailed logos, this bug would be invisible — Homey UI shows boiler off, everything looks OK. Insight came from EventLog grep hold_off_*.

The bug was categorized as "state machine cold start" — which typically appears in software once per project and then never. Here, however, the house, which takes place again every morning, has constant cold-start exposure (after every power outage, after every deploy, after every Homey restart).

Defense in depth: sh_brain_guardian_v1 (V1 LIVE from 26.4.) has the invariant "if the boiler is forever held off + the zone is slowly decreasing → alert". This meta layer would have caught the same bug within 15 min even if the v1.2 fix didn't exist.
