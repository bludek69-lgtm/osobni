Memory pressure — 6 live patches and bathroom audio reset

The second half of May 14. In the morning, the RPi/HAOS infrastructure was cleaned (sandbox 24/7, kiosk Phase E, dashboard cache retry — separate post). In the afternoon, however, he began to delve into one specific symptom: the bathroom sometimes left the lights on and the radio playing long after we left. A realistically seen problem, recurring, not an edge case.

Here's how it turned into 6 live patches to Homey in one day. No chaos. Sandbox-first, drift check, rollback ready, SHA bit-perfect verify on every PUT.

Phase R0 — what really hurts

Read-only preflight via sandbox runner + Homey REST + watchdog log + EventLog. Three numerical findings immediately gave context:

  • HomeyScript app status running, but the memory oscillated 99-154 MB over 24 hours, threshold 125 MB
  • 38 restart_triggered in the watchdog log in 24 hours. On average one reboot every 38 min, but clustered every 5-10 min during high-mem phases
  • HomeyScript cumulative crashed counter 1906

But the sandbox runner gate showed DEPLOY_GATE_OPEN, 20/20 PASS tests. Sandbox infrared OK. The problem was elsewhere — in the real runtime stability of Homey.

Phase R1 — root cause classification, not guessing

The R1 prompt had an explicit enum of 11 possible root cause tags (FLOW_MISSING, WRONG_FLOW_CARD, STATE_NOT_WRITTEN, SCRIPT_CRASH_INTERRUPTED, VACANCY_GUARDIAN_NOT_ENFORCING, etc.). The goal: to fit into one or more categories, not to have a fluffy diagnosis.

Diagnostics showed:

  • sh_vacancy_guardian_last_run_ts = '2026-05-14T06:25:02Z' — guardian last finished 67 minutes ago
  • sh_audio_current_mode stuck on 'radio_bathroom' from the morning routine (~03:30Z)
  • sh_audio_active_speaker stuck on 'Speaker koupelna'
  • 5 vacancy decisions / 24h in EventLog (expected ~288 = 5min × 24h)
  • Motion ages in vacancy decisions: 13,686 s, 9,456 s, 4,685 s, 4,056 s, 2,286 s — light/audio ran for up to 3.8 hours after leaving the bathroom

Classification: VACANCY_GUARDIAN_NOT_ENFORCING primaries + STATE_NOT_RESET secondary (audio mode does not reset itself).

Phase R1 FLOW VERIFY — elimination of bad hypothesis

Hypothesis #1 was: cron Flow is broken. Classic intuition, often correct. But sandbox-first wants empirical evidence, not intuition. Pull all 233 advanced flows via REST, find the flow that calls the guardian script, inspect cards: 

Flow a996ffa1 — "SH – Vacancy – Guardian Cron 5min"
  enabled: true
  broken:  false
  trigger card:
    id:   homey:manager:cron:every_nth         ✅ správný cron format
    args: { n: 5, type: "minute" }              ✅ správné argumenty (T6+T15 valid)
  action card:
    id:   homey:app:com.athom.homeyscript:run
    args.script.id: 718292bb-...                 ✅ matches sh_room_vacancy_guardian_v1

Flow is structurally 100% correct. Eliminated hypotheses: FLOW_MISSING, FLOW_DISABLED, FLOW_BROKEN_CARD, FLOW_WRONG_SCRIPT_TARGET.

No flow is broken but runtime kill mid-flight. The watchdog log confirmed it: a cluster of restarts exactly around the last guardian run (06:20, 06:25, 06:30 — guardian completed at 06:25, killed cluster at 06:30).

Heartbeat patch — CRASH_MID_RUN proof without guessing

A key pre-deployment problem: we only had one timestamp (sh_vacancy_guardian_last_run_ts written at the end run()). When he was still, it was impossible to distinguish:

  1. "cron Flow is broken and won't fire guardian at all"
  2. "cron Flow fires, but guardian kills mid-flight"

Patch: add the second timestamp at the beginning run() — sh_vacancy_guardian_heartbeat_ts. When cron fires and the script calls at least once setValue, the heartbeat will be recorded. If the script then runs out, last_run is also written. Pair logic: 

both fresh        → OK_completing
heartbeat fresh,
last_run stale    → CRASH_MID_RUN  ← runtime kill během exekuce
both stale        → CRON_NOT_FIRING ← cron flow / app dead
mixed             → WARN

Sandbox test T26 5/5 PASS. Replay scenario guardian_heartbeat_crash_mid_run.json simulated the exact production situation.

Two small live changes — var and guardian v1.1

Needed before guardian v1.1 deploye new Logic variable: 

POST /api/manager/logic/variable
body: { "name": "sh_vacancy_guardian_heartbeat_ts",
        "type": "string", "value": "" }
→ HTTP 200
→ id: 1514bec1-7a87-4d22-b3c7-16ce185a2e79

Idempotent guard pre-check confirmed that var does not exist. POST. Verify post-GET. Audit JSON to rollback/var_create_sh_vacancy_guardian_heartbeat_ts.json. No script has used it yet — safe isolated addition.

Then guardian v1.0 → v1.1: 273 lines → 309 lines, two small edits — heartbeat write at top of run() + bathroom-specific stuck-state reset when vacancy confirmed. Backup pre-deploy live source pulled, SHA compared with pre-staging backup (drift check), PUT, re-GET, SHA bit-perfect verify.

First cron after deployment — sandbox-first vindication

PUT took place at 08:01:13Z. Next 5-min cron at 08:05:00Z. Sample at 08:05:29Z: 

sh_vacancy_guardian_heartbeat_ts = '2026-05-14T08:05:00.138Z'  ← ✅ fresh
sh_vacancy_guardian_last_run_ts  = '2026-05-14T07:55:02.351Z'  ← ❌ stuck 10 min

CRASH_MID_RUN diagnosis immediately proven. Heartbeat fire-d (cron OK, script started), last_run NOT written (script killed mid-flight). The same pattern observed at 08:10, 08:15 cron firings.

This confirms hypothesis R1 FLOW VERIFY: not flow, but runtime. Pivot to R2.

Phase R2 — memory pressure audit

R2 read-only audit pull of all 132 resource scripts + cron inventory. The number that stops: 1,295.7 cron fires per hour across 67 cron flows. 21 fires per minute average. Worst offenders:

  • sh_tts_orchestrator_v1: 240/h = every 15 s (TTS queue processor, fires regardless of queue state)
  • sh_shelly3em_poller_v1: 120/h = every 30 s
  • sh_pracka_done_detector_v1: 60/h
  • sh_morning_kaffe_check_v1: 60/h
  • sh_wake_confirm_v1: 60/h
  • sh_time_sync_guard_v1: 60/h
  • sh_intent_engine_v1: 60/h
  • … 60 additional cron flows at frequencies of 30/h-1/h

Every fire = fresh V8 sandbox spawn in HomeyScript app. Even if the work-load script was no-op, lib eval + var load + JSON parse takes 50-300 KB allocations. 1295 fires/h x 200 KB average = ~260 MB/h V8 heap churn. GC reclaim some, but net mem grows monotonically until threshold 125 MB → watchdog kill.

Quick Win Throttle — 5 patches with a clear rule

Strategy: minimum possible early-return guard on top of main entry of each worst offender script. No redesign, no features rewritten. Single if (...) return; block per script:

  • TTS Orchestrator: skip if sh_tts_queue empty AND sh_tts_queue_trigger idle. Saves ~180/h.
  • Coffee Check: skip outside Prague 04:00-11:00 window. Saves ~1,020 fires/day (70% of daily).
  • Wake Confirm: skip if user not sleeping AND hour ≥ 12. Saves ~45/h.
  • Wake Scorer: same logic. Saves ~20/h.
  • Morning Score: same logic. Saves ~45/h.

Per patch: pull live source, drift check vs pre-staging backup (catch case when someone edits the script via UI in the meantime), apply minimal patch via Python binary-mode (preserve CRLF), staging file with manifest + SHA256. Sandbox regression 26/26 PASS before every PUT. Bit-perfect SHA re-GET verify after PUT. JSON audit. 5 minutes of work per patch.

Sequential deploy — 21 minutes, 5 PUTs, no reboot

Per SAFE_REPAIR_MODE: one change, verify, next change. Timeline (UTC):

08:43:58  PUT sh_morning_kaffe_check_v1 v1.1   ✅ SHA bit-perfect

App state remained during all 5 PUTs running. Žádné nové crashy (crashedCount stable 1920 přes 21 min). Bit-perfect SHA verify on re-GET of each patch. Backup intact for per-script rollback (~10s single PUT).

9 minutes after the first deploy — bathroom audio finally idle

The main win did not expect a 24-hour soak. Sample 12 minutes after TTS deploy: 

Pre-deploy 08:26Z:
  sh_vacancy_guardian_heartbeat_ts = 08:25:00Z
  sh_vacancy_guardian_last_run_ts  = 07:55:02Z  ← stuck 31 min

Post-deploy 08:40Z (12 min after deploy):
  sh_vacancy_guardian_heartbeat_ts = 08:35:00.156Z
  sh_vacancy_guardian_last_run_ts  = 08:35:08.417Z  ← ✅ +8s = COMPLETED
  sh_audio_current_mode             = 'idle'         ← ✅ reset from 'radio_bathroom'

First successful guardian run in 40+ minutes. Stuck-audio-reset patch v1.1 got to the code in that iteration and reset it sh_audio_current_mode on 'idle'. A real visible fix to the primary user-reported problem — bathroom radio will no longer resume after a TTS notification because the mode is no longer pinned to radio_bathroom.

What this day was NOT

  • It wasn't a flow edit. Sandbox-first elimination of the flow problem freed up hands for a proper fix (script-level throttle + heartbeat).
  • It wasn't chaos. Six live changes during the day, but each was a single PUT with pre-flight + drift check + audit + verify.
  • It wasn't a PC export. Phase E kiosk was rebuilt fresh from RPi/SSH without any reading from C:\. Heartbeat var + guardian v1.1 + 5 throttle patches all originated on HAOS staging dir, not PC.
  • It's not done. The watchdog restart rate has not yet fully decreased during baseline monitoring (+30 min mark). Throttle savings accumulate slowly. Recommended 2-6h soak before the next decision (Shelly poller offload, log buffer, etc.).

Five hard rules that hold all this together

RulesHow it manifested itself in R2
SANDBOX-FIRST 26 sandbox tests + 19 replay scenarios PASS before every PUT
AUTO-REGISTERS New var sh_vacancy_guardian_heartbeat_ts added with JSON audit; sandbox runner registry baseline preserved
SAFE_REPAIR_MODE Per-script live backup pre-PUT, SHA drift check, bit-perfect verify, rollback documented as single PUT ~10s
REUSE FIRST No new HomeyScript. 6 patches = update existing scripts. Sandbox tests T22-T26 were created in the existing framework.
RPi/HAOS infrared rules Everything pulled via Homey REST + HAOS sandbox staging dir. No PC read in R2.

What will the soak show

Sandbox runner runs every hour as a 24/7 gateway. Pair-logic diagnosis sh_vacancy_guardian_heartbeat_ts vs sh_vacancy_guardian_last_run_ts will provide a continuous counter:

  • OK_completing rate (how many of the 288 fires/day actually complete)
  • CRASH_MID_RUN rate (how many starts killed)
  • Watchdog restart trend per hour
  • Bathroom audio_mode reset frequency (how many times guardian executes patch B)

If after 2-6 hours the restart rate falls below 20/h, R2 Quick Win considered success. If 20-30/h remains, another candidate is Shelly poller offload on RPi Python (eliminates 120/h fires). If still >30/h, deeper problem — log buffer offload, cache patches, maybe HomeyScript app version upgrade.

Takeaway

Six live hits on a production Homey in one day is a lot. It would be risky without sandbox-first. With 26 sandbox tests + 19 replay scenarios + per-script SHA verify + JSON audit for every PUT, but speed does not mean chaos.

And the real user win — bathroom radio will no longer resume from an empty bathroom — was measurable 9 minutes after the first deployment. Not in a week. Not with "it will get better in time". Measurable timestamp, provable fix, sandbox replay scenario that reproduced the situation beforehand.
