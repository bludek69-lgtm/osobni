UUID re-pair orphans — silent fail after battery replacement

I open the window in the dining room, the air purifier continues to run. It should turn off — flow trigger on alarm_contact open has been working without problems for a year. But not today. No error in UI, no alert, just silent fail.

After replacing the flashlight in the Door/Window Sensor Jidelna1 a week ago, the Homey device received a new UUID. Three flows referencing the original UUID are orphaned. This is the story of diagnostics and bulk fix.

Symptom

Door/Window Sensor Dindelna1 works normally from a capability perspective — I can see in Homey UI alarm_contact value, real-time changes when opening/closing. The tile on the dashboard is responsive. The sensor is not dead, it is communicating, sending data.

But the flows that were supposed to react to change events — they don't respond. No flow run log, no error. Trigger karta v UI vypadá normálně, žádné červené upozornění. Senzor existuje, flow existuje, jen mezi nimi chybí spojení.

Affected flows

  1. SH - Cistic - Window Open — turns off the purifier when the window is open (no need to filter the outside air)
  2. SH - Heating - Window Open — will reduce the bathroom + dining room target by 2 °C when the window is open (heat loss compensation)
  3. SH – Lights – Privacy Bypass — temporarily releases the privacy guard when the window is open (assumes user activity)

Diagnosis

I tried several checks: 

# Senzor existuje?
GET /api/manager/devices/device/<jidelna1_uuid_in_flow>
→ 404 Not Found

# Senzor v device list?
GET /api/manager/devices/device
→ vidím "Door/Window Sensor Jidelna1" ale s JINÝM UUID

# Compare:
flow_uuid: 5c3a8e21-b4f2-4a91-9d1c-7e8f6a2b3c4d
real_uuid: 9f4c2e88-3a7d-4f5b-b2e6-1c8a9d5e7f3b

Old UUID (in flow trigger card) vs. real UUID (current device) is different. After replacing the battery on 19.4. (memory snapshot) Homey generated a new UUID. The old UUID in 3 flows remained as an orphan reference — a device that "doesn't exist" (404), so the trigger never fires.

Why is it not an error?

Homey flow trigger system has graceful degradation for missing devices — instead of error only never fires. This makes sense for robustness (one offline sensor shouldn't bring down the entire flow system), but it means silent fail.

No "this flow refers to a non-existent device" UI indication. No alert. No flow run log entry. A bug is only visible when you expect something to happen and nothing happens.

Fix — bulk swap

A manual fix per flow via the UI would mean opening each flow, finding a trigger card, remapping to a new device. Three flows = three minutes manually. He wants automation for future incidents (and future battery changes). 

# 1. Najdi všechny flows referencující old UUID
flows = GET /api/manager/flow/advancedflow
broken = [f for f in flows if old_uuid in str(f.cards)]

# 2. Per broken flow: PUT s nahrazeným UUID
for flow in broken:
  for card in flow.cards:
    if card.deviceId == old_uuid:
      card.deviceId = new_uuid
  PUT /api/manager/flow/advancedflow/<flow_id> flow

Bulk swap took place, 3 flows fixedly. Test: I open the window, the cleaner turns off. Function restored.

Backlog — preventive scanner

This is an expected incident — battery replacement happens every year+, and each re-pair generates a new UUID. Reactive fix per incident is not scalable.

Backlog: tools/find_orphan_device_refs.py — prevention scanner that runs before every commit (or daily cron). Iterates flows, compares device IDs with current device list, reports orphan refs. 

# tools/find_orphan_device_refs.py (návrh)
from homey_api import get_devices, get_flows

def main():
  devices = {d.id for d in get_devices()}
  flows = get_flows()
  for flow in flows:
    for card in flow.cards:
      if card.deviceId and card.deviceId not in devices:
        print(f'ORPHAN: flow={flow.name} card={card.id} '
              f'orphan_id={card.deviceId}')

What was learned

Silent fail is the worst category of bug. You see the result (cleaner does not run), you have no idea the cause (no error). Diagnose requires system-wide state inspection, not log reading.

Lessons:

  • Re-pair = new UUID. Expect orphan flow trigger refs after every battery change / re-install. It's not a Homey bug, it's a design choice (UUID stability vs. clean slate).
  • Test after each battery change. A simple smoke test — open the window, does the cleaner turn off? No? Diagnosis.
  • Preventive scanners > reactive fixes. Better to spend a minute a day verifying an invariant than an hour fixing an incident.
  • Brain Guardian extension. This invariant belongs to the guardian — checked periodically, no orphan device IDs in flows. In the plan.

UUID stability in the smart home world is an issue that will escalate with each new device. Aqara P2 (Matter/Thread) replacement for SNZB-04 adds another permutation where re-pair after Thread network change generates a new ID.

General principle: never reference the device directly via UUID in user-facing code. Instead via name lookup (resolve at runtime) or device map abstraction (one place to update). The current architecture does this for scripts (sh_device_map_v1), but not for flow trigger cards — a Homey UI limitation.
