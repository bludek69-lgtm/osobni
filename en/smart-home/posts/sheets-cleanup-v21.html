Big Sheets layer cleanup — 28 sheets, 6 commits, one day

On Monday, May 5, the morning routine did not start at all. Instead of just fixing that particular bug, I opened up the entire Google Sheets layer and looked at what was actually stored in it. The finding was unpleasant: half of the sheets were dead code — either no one filled them in, or the data flew somewhere other than where it was supposed to go.

The day ended with 8 commits, Apps Script v18 → v21, fixed dashboard graphs and 3 sheets deleted from Sheets. Here's what was revealed and fixed.

1. Morning routine: sleep_window blocked everything

It started with a simple complaint: "morning routine didn't start at all today". Alarm clock at 3:12, motion sensor in bedroom at 3:16:23, but morning brain script just logged waiting_2nd_motion and got stuck quietly.

Root cause: variable sh_sleep_window_until_ts was set to 2026-05-05T06:37:51Z (= 08:37 local time) — 8 hours since pressing the sleep button late at night. Morning open-space router saw spim=no, sleep_window=yes and everything was blocked by reason= sleep_window_guard. It was never cleared when the user woke up — no one had the responsibility to clear that flag.

Second problem: the same lights turned on by themselves at night even though active sleep_window. Investigation: sh_light_router_v1 just checked sh_spim === 'yes', NO sh_sleep_window_until_ts. Open_space_router had this defense since 3.5, but light_router did not. When sh_spim flickered on no (due to time_sync_guard reset), the evening light request passed and Sektorka1 lit up at 22:36.

Fix:

  • sh_wake_confirm_v1 — when multi-zone wake confirm confirms the wake (sh_jsem_vstal=strong_yes), centrally clear window TS. Single source of truth, not per-router.
  • sh_light_router_v1 v1.15 — parity with open_space router. Block SLEEP_BLOCKED_REQUESTS even if sleep_window active + strong_yes override.

2. Score producer existed, but no one read it

I delivered yesterday sh_morning_score_v1 — an adaptive engine that evaluates 10 sensors every minute and calculates a morning score 0-100 + state machine (night_sleep, pre_wakeup, wakeup_candidate, morning_confirmed, …). Cron 1×/min ran, vars updated, but… nobody read it. Brain decided according to his own 180s motion debounce and ignored the score.

That's why the morning routine didn't start. Score would say morning_confirmed at 03:18 (after wake_confirm strong_yes), but the brain did not receive any signal for re-trigger. Single bedroom motion → wait_2nd_motion → 180s window → no 2nd motion in bedroom (user went to bathroom) → debounce never timed out.

Fix:

  • sh_morning_brain_v1 — added scoreBypass parallel to the existing one wakeBypass. If sh_morning_state ∈ {morning_confirmed, wakeup_candidate} and heartbeat fresh (<5 min), bypass debounce.
  • sh_morning_score_v1 v1.4 — alarm-aware (probe Homey.alarms.getAlarms(), ±30 min window, +3 score), state transitions logged to EventLog, dual-log to the new Morning State Timeline sheet (16 columns).

3. Sensor register — adaptability for future sensors

The second shortcoming: the sensors in the score script were hardcoded names. New sensor in the room = code edit. PROMPT for the adaptive routine asked for pattern registers.

Implemented:

  • New variable sh_wakeup_sensor_registry — JSON with 10 sensors, each with metadata: device, capability, room, type, morning_weight, night_weight, use_for_wakeup, reliability, rule, is_legacy, note.
  • Populator script _create_morning_sensor_registry_vars_v1.js — idempotent create+update.
  • Score iterates registers, non-legacy entries (is_legacy: false) automatically contribute +morning_weight if sensor recently active <300s.

Workflow for a new sensor: edit registry → add entry s is_legacy: false, weight, use_for_wakeup: 'yes' → re-run populator. Score is automatically used from the next cron tick. No code editing.

4. Dashboard fetchy → 404 (silent)

The dashboard audit showed that 4 endpoints in Apps Script do not exist at all, but the dashboard calls them: 

?mode=lux_history       → fall-through na default filter
?mode=battery_history    → totéž
?mode=morning_timeline   → totéž
?mode=diagnose           → jen v tooltip (ne fetch)

Apps Script didn't return a 404 — it did {rows:[]} (default filter response). He checked the dashboard data.points or data.events (which didn't exist) and showed "No data (run context_full_v1)" message. It looked like a broken producer, but actually a broken endpoint.

Fix Apps Script v20: 3 new endpoints:

  • mode=lux_history&hours=24 — Lux Monitor sheet → {points: [{ts, lux_j, lux_k}]}
  • mode=battery_history&days=30 — Battery History → {points: [{ts, device, battery}]}
  • mode=morning_timeline&days=3 — MERGE Morning State Timeline + Rani routine + TTS Monitor (filtered hour 03-11 Prague) → {events: [...]} sorted DESC, cap 500.

5. Leaves without produce

Audit Sheets layers: 28 sheets in total, but the reality:

  • 12 active — daily log, dashboard reads (EventLog, Zone Activity, TTS Monitor, FlowLog, EnergyLog, …)
  • 4 periodic — depend on events (Daily Report, Gemini Briefing, EnergySummary, Ranni_Rutina_Budik)
  • 6 dead-code routing — data goes to EventLog instead of a dedicated sheet (System Health, Test Results, Audio Debug, Manual Actions, Logs, Gemini Diagnostics)
  • 5 without producing at all — 0 řádků, ale Apps Script má pro ně handlery (AI Tasks, ExceptionLog, Config, SanityLog, DataQualityReport)
  • 1 is waiting — Morning State Timeline (deploy v20)

They have 5 leaves without produce 2 diagnostic value (ExceptionLog, SanityLog), 3 are useless (AI Tasks, Config, DataQualityReport).

ExceptionLog: the infrastructure works, only the scripts do not fail

The ExceptionLog list had 0 lines, but it has 24+ scripts logException() in catch blocks. Test: POST directly via API → row was written → infrastructure OK. The empty state simply reflects production stability — the scripts do not fail often enough to fill the sheet. Left unchanged, waiting for the first real exception.

SanityLog: validator patch for per-item logging

SanityLog had 0 rows and 0 producers. sh_state_validator_v1 aggregate is already logging validator_issues event to EventLog, but per-item detail (drift, stuck, conflict) is not written anywhere.

Patch v1.x: after existing EventLog summary log dual-logs per-item rows to SanityLog (warning_type, severity, zone, details, details_json). Bug E ghost (priority_active=light without request) will be caught on the next dirty cycle.

3 leaves deleted

Apps Script v21 removes:

  • AI Tasks — workflow tracker, dashboard reads 0 rows but never.
  • Config — centralized config never used.
  • DataQualityReport — energy data quality daily snapshot, unused.

Deleted from Apps Script: SHEETS entries MAX_ROWS, ensureAllSheets_ headerMap, headers constants, mode=tasks + mode=config endpoints, event_type='ai_task' POST handler. From Google Sheets manual delete via right click. Out of 5 dashboards AI Tasks panel display:none + loadAITasks() no-op stub.

6. DeviceInventory: never sent by producer

The DeviceInventory list should have been refreshed every 6 hours by cron flow SH – Energy – Device Inventory Cron 6h. The script sh_device_ inventory_guard_v1 ran, the vars updated, but the leaf stood for 5 days.

Reason: script just updates internal vars (sh_device_measurement_registry_json etc.) but never POST to Apps Script. Apps Script has a handler for mode=device_inventory POST from v18 but no producer called him.

Fix v1.1: added fire-and-forget POST registry → Apps Script at the end of the script handleDeviceInventory_ transforms to batch rows. After deployment, the list received 82 devices snapshot.

7. Dead-code routing — a historical finding

Key architectural bug: logEvent() lib is pushing sheet: 'EventLog' in the payload. Apps Script routeEvent_ check p.sheet as FIRST — if 'EventLog', routes there and returns. event_type routing for System Health, Manual Actions, Audio Debug, Test Results, Gemini Diagnostics will NEVER be reached.

That is these 6 sheets have been stagnant for 3+ weeks not because the producers are not working, but because the data is flying into the EventLog instead. The data is not lost (it is in the EventLog), just in the "non-optimal" sheet.

Pragmatic decision: leave as a historical reserve. Sheets preserved, the dashboard does not read them, they would only be deleted if they made a mess. Apps Script handlers preserved — if I ever wanted to fan-out (write to EventLog AND dedicated sheet), it's a 3-line patch per sheet.

Final status

25 sheets (from 28 in v20), 3 deleted, 6 commits, deploy without incident (one HomeyScript app crash + recovery — memory bloat ~95 MB / 125 limit, normal within today's operational latitude).

Audit: all expected sheets exist, no collateral. SanityLog + ExceptionLog ready. Morning State Timeline waiting for the first state transition. Lux + Battery + Morning Timeline dashboards started showing real data after deploy v21.

Lessons

1. The producer-only component is a red alert. If someone produces "X produces data, Y consumes it", and Y is never replenished — the system has a long-term silent fail tendency. sh_morning_score_v1 he ran for a month without a consumer and no one cared until the morning routine collapsed.

2. Default values in the lib API are an architectural bug. sheet: payload.sheet || 'EventLog' it looked like a sensible default. It was really pushing all of them event_type events into one sheet and dead routes were created over half a year without detection.

3. Delete only what you are sure no one is missing. Out of 5 sheets without production, 2 have a diagnostic value (ExceptionLog, SanityLog). 3 are unnecessary. 6 dead-code sheets have archival value — the data is not lost, just in another location. Conservative deletion, mandatory post-deployment audit.

By the way, next week's Monday morning routine will already run with a full pipeline: alarm-aware score → state transition log → scoreBypass in brain → registry auto-discovery + Bug E ghost detection via SanityLog. If something fails, EventLog + Morning State Timeline + ExceptionLog will give a detailed timeline of reasons.
