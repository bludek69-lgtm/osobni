Three weather sources → one. LOCATION_TIME_GUARD day.

The briefing recited to me on Monday morning that it was 13°C outside. It was actually 6°C. At 3:03 that night — while I was still fast asleep — the morning briefing started by itself, turned on the lights, and began playing the news for me into the empty kitchen. And if that wasn't enough: the same system could say "good morning" at 3:30 in the morning if something detected movement in the bedroom.

Three problems. Two days. This post is about how one day of repairs resulted in a layer LOCATION_TIME_GUARD and yr.no became the single source of truth for location, time and weather in the entire system.

Symptom #1 — Thirteen degrees on an overcast morning

He read the briefing script in the morning: "It's 13 degrees outside, partly cloudy." I looked out the window. Fog, rain, 6 °C according to the thermometer. The script didn't lie — it just read an empty cache (sh_weather_3d_json = []) and fell on a fallback value that was hardcoded somewhere in the code from way back when.

What it showed was worse than "the cache is empty". The audit revealed three parallel weather sources in one system:

  1. yr.no application in Homey (Norwegian Meteorological Institute, free, native forecast). It had 18 capabilities and worked perfectly — but no one read it.
  2. OpenWeatherMap fetch v sh_context_full_v1.js. HTTP call to api.openweathermap.org with hardcoded GPS coordinates flat (LOCATION_REDACTED). Key in Homey variable. Functional but duplicate.
  3. Open-Meteo fetch v sh_weather_fetcher_v1. My own HTTP fetcher from earlier in the week, which I added before I knew yr.no was already there. Location: Prague (default 50.0875, 14.4213).

Three sources. Two different cities. None of them were clearly "the right one". And the worst: meanwhile, the dashboard directly called OpenWeatherMap in the browser (third HTTP fetch in the UI layer). Plus one hardcoded fallback in the code in case none of this works.

Symptom #2 — Morning routine at 3:03am

On Tuesday morning, my lamp came on and he started the briefing. Looking at the clock: 3:03. The alarm was supposed to go off at 3:13 (Mon-Fri). I didn't get up. What happened?

Diagnostics via EventLog: 

03:03:00  motion bedroom (SNZB-03) — TRUE
03:03:02  sh_morning_brain_v1  → brain_invoked (motion, briefing2 audit)
03:03:02  sh_morning_brain_v1  → morning_score_bypass (score=85, bypass 180s debounce)
03:03:05  sh_audio_brain_v2    → audio_dispatch (radio_kitchen)

03:13:01  alarm "Do Prace" fires
03:13:02  sh_morning_brain_v1  → alarm_late_ignored (already up)

Score scorer gave the movement a score of 85 (out of 100). 8 raw points were enough to start. Schedule: 

+2  cas>=03:00 (morning window)
+10 wake_confidence_score=50          ← bedroom motion
+1  jsem_vstal=yes
+3  open_space_dual (FP2+motion)      ← BUG
+1  telefon_doma
= raw 17 → final 85 (multiplier ×5)

Key nail: open_space_dual (FP2+motion) +3. FP2 is a mmWave presence sensor in the dining room/kitchen. Motion is a Fibaro PIR. Zone Activity showed something scary: 

00:04 UTC  snzb06p=TRUE  fibaro_motion=TRUE  idle_open_space_s=17161
00:14 UTC  snzb06p=TRUE  fibaro_motion=TRUE  idle_open_space_s=17761
00:24 UTC  snzb06p=TRUE  fibaro_motion=TRUE  idle_open_space_s=18361
...
01:03 UTC  snzb06p=TRUE  fibaro_motion=TRUE  idle_open_space_s=20760  ← motion bedroom
01:04 UTC  snzb06p=TRUE  fibaro_motion=TRUE  bedroom_active=TRUE

Both sensors remained TRUE all night. The idle counter was increasing (= no one was moving), but the flag was still TRUE. Stuck state from the previous evening. Then in the morning when SNZB-03 detected micro-motion in the bedroom (turning in the bed? draft? cat?), the scorer crossed off all 17 points and gave me final score 85.

The bug was not in the sensors. The bug was that the scorer counted the stuck-TRUE flag as a fresh signal.

Symptom #3 — "Good morning" at half past three

The last pocket enemy was the tightly hardcoded greeting function in the briefing script: 

function buildIntro(hour) {
  if (hour < 6) return 'Dobré ráno, Luďku.';
  if (hour < 12) return 'Dobré ráno, Luďku.';
  ...
}

"Hour < 6" meant that if anything was triggered at 2:30 (such as the false-positive wake described above), the system would start the morning briefing with "Good morning". At night. It didn't make sense.

Fix — Consolidate to one source of truth

Step 1: YR.no as a single weather source

New script sh_weather_yr_bridge_v1.js: reads directly from Homey Weather device (yr.no driver), every 10 minutes, writes to 22 variables: sh_weather_temp_now, sh_weather_temp_feels_like, sh_weather_temp_min_6h, sh_weather_temp_max_6h, sh_weather_humidity, sh_weather_pressure, sh_weather_wind_speed, sh_weather_wind_dir, sh_weather_rain_1h, sh_weather_rain_6h, sh_weather_cloud_pct, sh_weather_uv, sh_weather_now_desc (English), sh_weather_now_desc_cs (Czech), sh_sunrise_hhmm, sh_sunset_hhmm and others.

Czech translation of the weather description in the bridge script ("Cloudy" → "Cloudy", "Light rain" → "Light rain", etc. — 30 values in the translation map). The location is taken from yr.no device settings (Homey UI → Weather → Advanced → lat/lon/altitude). When the user corrects the location in the application, the bridge automatically catches it — no HTTP fetch, no API key.

Deleted:

  • sh_weather_fetcher_v1.js (Open-Meteo) + cron flow — duplicate
  • fetchOWMWeather() v sh_context_full_v1 (−2,868 dead code characters)
  • A variable sh_owm_api_key
  • A constant WX_LAT, WX_LON in dashboards (legacy hardcoded GPS)
  • Direct OpenWeatherMap HTTP call in dashboard JS (browser no longer uses API key)

Step 2: Score scorer fresh-trigger guard

sh_morning_score_v1 bumpnut to v1.6 with new protections: 

// Před: value === true OR ageS <= 300
const recent = (info, windowS) => info.exists && (info.value === true || info.ageS <= windowS);

// Po: jen čerstvá detekce (motion fired v posledních 300s)
const fresh = (info, windowS) => info.exists && info.ageS <= windowS;

// Plus stuck-presence detector
const isStuckPresence = (info) => info.exists && info.value === true && info.ageS > 3600;

Open-space bonus is applied only if FP2 and motion fired in the last 5 minutes. If they were TRUE from the evening (stuck), the bonus is not applied: 

+0  open_space_stuck_skipped (FP2_age=111315s, kitch_age=337s)

Plus PRE_ALARM_HARD_CAP — if the hour is 3 and the nearest alarm is more than 5 minutes away, the score is capped at 6 (status pre_wakeup, ne morning_confirmed). No running routines.

Step 3: LOCATION_TIME_GUARD layer

Here was the major turning point. Central script created instead of per-script time/phase logic sh_location_time_context_v1.js, which counts every 5 minutes: 

{
  "timezone":      "Europe/Prague",
  "is_dst":        true,
  "utc_offset":    "+02:00",
  "local_time_iso": "2026-05-12T07:32:41",
  "local_hour":    7,
  "latitude":      …,         ← LOCATION_REDACTED
  "longitude":     …,
  "altitude":      489,
  "city":          "LOCATION_REDACTED",
  "country":       "CZ",
  "sunrise_local": "05:14",
  "sunset_local":  "20:35",
  "day_phase":     "morning",   ← smart-computed
  "weather_source":"yr.no",
  "weather_health":"ok",
  "location_health":"ok",
  "time_health":   "ok",
  "status":        "ok"
}

The day is not divided according to hardcoded hours ("morning = 5-10"), but according to the actual sunrise and sunset from yr.no. morning = from (sunrise − 1h) to (sunrise + 4h). night = between (sunset + 1h) and (sunrise − 1h). In our country, May 12, 2026: sunrise 5:14, sunset 20:35 — so morning = 4:14–9:14, evening = 18:35–21:35.

Step 4: Briefing greeting guard

function buildIntroByPhase(phase, hour) {
  if (phase === 'night')   return 'Vítej, Luďku.';       // NIKDY "dobré ráno" v noci
  if (phase === 'morning') return 'Dobré ráno, Luďku.';
  if (phase === 'day')     return 'Dobrý den, Luďku.';
  if (phase === 'evening') return 'Dobrý večer, Luďku.';
  // Fallback: hour-based, ale 0–5 = "Vítej"
  if (hour < 5)  return 'Vítej, Luďku.';
  ...
}

He is reading the briefing now sh_day_phase_context from master JSON and at night it will say "Welcome, Luďka" instead of "Good morning".

Step 5: Morning brain phase_guard

Defensive layer in sh_morning_brain_v1. If sh_day_phase_context === 'night' and the alarm did not occur today, the motion-trigger is ignored: 

if (event === 'motion_detected' && alreadyTriggered !== 'yes') {
  if (dayPhase === 'night' && !alarmFiredToday) {
    return 'PHASE_GUARD_BLOCKED';
    // Log EventLog: event='morning_routine_blocked_wrong_phase'
  }
}

"Good morning, Ludik. It's 7:33 a.m., the date is May 12, 2026. It's 5 degrees outside, feels like 2, cloudy. Between 5 and 8 degrees during the day. The sun sets at 20:35. System health is 92 percent…”

Briefing now reads five sources he understands. Temperature correct. By feel (difference ≥2 °C). Min/max during the day. Sunrise/sunset (according to time of day — it says sunrise in the morning, sunset in the evening). And at night he would say "Welcome, Ludka", not "Good morning".

What I learned

  1. Smart home tends to buy sources of truth. When I add a function, I usually don't check in my head whether similar data already exists anywhere in the system. After some time, the audit will show that I calculate the same data three different times. Consolidation hurts, but saves hours of diagnostics.
  2. Stuck-TRUE flag is not a fresh signal. mmWave radars and PIR sensors can remain TRUE for hours. If I take them as "the movement just happened", I'm lying to myself. The difference is in ageS — when the value last changed, not what the current value is.
  3. "Good morning" at night is more than a UX bug. It's a symptom of the system not knowing what day it is. Greeting function counted hour. But it's supposed to be 3:00 in the morning night, ne morning. The central layer knows it right — according to sunrise from yr.no, not hardcoded "< 6".
  4. Memory rule "REUSE FIRST". The yr.no application in Homey has been installed since the system was founded. It had 18 capabilities and it worked. I didn't know about it and added the Open-Meteo HTTP fetch from the beginning of the week. Audit finds these duplicates and throws them out.

What's next

The LOCATION_TIME_GUARD central layer is deployed. Refresh every 5 minutes via cron flow. If the status falls to watch or warning, another flow logs a warning. If it falls on critical (for example yr.no offline for more than 2 hours), the full morning routine must not be run without an additional check. Safety guard.

Consumer audit — seven other scripts that until now had their own time/phase logic — is gradually migrating to single source. Sync variables sh_cast_dne z sh_day_phase_context today it already solves most legacy reads without the need for a per-script patch (NO REGRESSION rule).

Tomorrow morning (Wednesday, alarm at 3:11 Mon-Fri schedule) I will do an automatic check — if phase_guard catches the motion-trigger in the night phase, if the radio plays after the second briefing (TTS resume v1.9 — another bug, separate post), if the briefing again has the correct temperature from yr.no.
