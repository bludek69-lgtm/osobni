Sandbox 24/7 + kiosk Phase E + cache retry — cleaning day

The day RPi/HAOS stopped playing service assistant and became a full-fledged test gateway between development and production. Three layers at the same time: a Python sandbox runner running 24/7, an RPi kiosk with a cache-first fallback chain and a dashboard cache pipeline that no longer sulks at the occasional 417 from Athom relay.

No Homey write, no edit dashboards on HAOS, no device renames. Three gates simultaneously — SANDBOX-FIRST, AUTO-REGISTRY, SAFE_REPAIR_MODE — keeps the entire progress sandboxed until it's confirmed that it won't break anything.

Node.js to HAOS without pain

First observation of the morning: HA SSH addon on RPi does not have Node. Sandbox gets Node up to the persistence layer core_ssh apks config — i.e. Supervisor automatically reinstalls it every time the addon starts, so addon rebuild doesn't blow it. 

# Before
apks: ["python3"]
# After (LIVE, persistent přes Supervisor)
apks: ["python3", "nodejs", "npm"]

Verification: node -v → v24.14.1, npm -v → 11.11.0, the smoke test reads all 6 snapshot fixtures (devices/variables/zones/scripts_index/sh_dashboard_data/sh_device_map) without error. After addon restart Node survived → persistence confirmed.

Phase D — sandbox 24/7 in HA automation

Sandbox-side tests run once. A regular runner was waiting for us 24/7 — shell_command called by HA automation every full hour. The first attempt failed miserably. 

2026-05-14 07:00:00.341 ERROR (MainThread)
  [shell_command] Error running command:
  `node /config/smart-home/sandbox/runner/sandbox_runner.js`,
  return code: 127

Exit 127 = node: command not found. The HA Core container does not have a Node — our Node persistence was in the core_ssh addon, not in the main HA Core. Two isolated docker layers. Pivot: runner rewritten in Python (HA Core has Python 3.12 natively), Node sandbox layer remains as development.

F1-A programmed Python orchestrator pure-stdlib, mirror 16-test matrix + replay JSON validator + 8-step gate logic (snapshot → tests → replay → regression → rollback → user_go). F1-B ported HA shell_command from node to python3. ha core check PASS, reboot, waiting for :00 cron, runs jumped from 4 to 5 at 06:00:00.956Z right on the minute mark: 

[runner_py] runs=5 tests=16/16 replay=OK
            blockers=0 gate=DEPLOY_GATE_OPEN

Gate semantics: DEPLOY_GATE_OPEN means "all technical checks passed" but still requires user_go: REQUIRED per change. Runner never interferes with live Homey himself. Just the verdict in the markdown report.

Auto-registries — gate against silent new entities

Whenever a new scene, automation, Flow, HomeyScript, dashboard widget, module, time mode, button, gesture or trigger is added to the system, the runner detects it during diff vs. baseline registers and marks as BLOCKED_UNTIL_TEST_EXISTS with a proposal for the name of the test and replay scenario.

Baseline registries now hold 8 scenes + 132 scripts + 232 advanced_flows = 372 entities. When the 133rd script is added, the runner sends a line of the type "scripts: sh_new_thing → propose tests_py/test_sh_new_thing.py". Live deploy without registry changes blocked.

Dashboard cache retry — fix over the weekend

Aside from the sandbox itself, one particular pipeline bug: dashboard cache script homey_dashboard_cache.py occasionally returned exit 1 in about 5% of cron firings due to transient errors from Athom cloud relay (vars fetch status=417 or connection drop). Failures were always transient — the next call (within 60 seconds) succeeded. Data loss = 0, just noise in the HA log.

Fix v2.1: homey_get divided into _homey_get_once + retry wrapper. Transient retry on {0, 417, 502, 503, 504} with backoff 0.5 s + 1.5 s, max 3 attempts. Permanent statuses (401, 404, ...) raise immediately without retry. 

RETRY_STATUSES = {0, 417, 502, 503, 504}
RETRY_BACKOFFS = (0.5, 1.5)  # 3 total attempts

Sandbox test T17 verified 5 case matrix (200 first try / 417+200 / 0+0+200 / 401 immediate raise / 417×3 exhausts) — 5/5 PASS. After deploying this morning the error rate dropped from ~5% to 1.8 % and the HA log no longer shows the hourly red line.

Kiosk Phase E — RPi-only rebuild

The kiosk (RPi 192.168.1.xxx with 1024×600 WaveShare display) was running HTML from 5/11 at 7:25 PM — a version that never knew the dashboard cache. When the HAOS-side cache pipeline started producing fresh JSON, the kiosk had no way of knowing about it. He still polled direct via server.py proxy to Homey REST.

The rule was strict: DO NOT READ ANYTHING FROM THE PC. The Phase E patch must be recreated directly from the HTML kiosk itself, not copied from PC dashboards/. Reason: PC may not be online and have old versions.

Workflow:

  1. SSH to the kiosk, pull /home/smart/dashboard/index.html + server.py at HAOS staging dir.
  2. Binary-mode Python patcher preserves CRLF line endings (kiosk file natively CRLF) — first attempt with LF-only produced a false 29,822-line diff instead of the real 112 lines.
  3. Patch HTML: replace 7-line fetchDashboardData() behind the 60-line version with a 3-stage chain cache→Homey REST→localStorage. Add #sourceBadge CSS + DOM element top-right fixed.
  4. Patch server.py: add /cache/dashboard-data.json route proxying HAOS /local/smart-home/dashboard-data.json, timeout 2.5 s, 502/504 fallback. Existing /api/* Homey proxy intact, HOMEY_TOKEN count unchanged.
  5. Sandbox tests T18 (loader fallback), T19 (cache proxy), T20 (visual contract). Run all 20 → 20/20 PASS.
  6. Backup to _backup_before_kiosk_phase_e_<timestamp>/ with SHA256 manifest + chromium command line snapshot.
  7. Atomic swap, reboot server.py (pkill + nohup), F5 reload Chromium via xdotool via DevTools port 9222.

After reloading the badge is really there. Orange ◐ CACHE OLD top-right — because HAOS cache returned JSON, but s _stale: true (bridge_age_s > 300 s). The Phase E chain has been preserved correctly, the dashboard has not remained blank, all control elements have been preserved.

Badge statuses:

  • ● CACHE — green, data fresh from HAOS cache
  • ◐ CACHE OLD — orange, cache OK but data older than 5 min
  • ○ HOMEY — blue, fallback to Homey REST
  • ○ LOCAL — red, fallback to localStorage last-good
  • ✕ ERR — all three stages failed

Takeaway

For this system, "I'll fix it in Homey" is no longer the first choice. The first is "I'll build a sandbox test that reproduces it, and only when it passes will I prepare a staging patch and wait for explicit GO". That's not red tape — that's the difference between a house where the bedside strip occasionally lights up by itself at night, and a house that can be tested without the resident reading about it in the build log in the morning.
