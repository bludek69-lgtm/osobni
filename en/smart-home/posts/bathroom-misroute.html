Bathroom misroute — 4 hours of diagnostics and fix v1.8

Last night at 20:45 the system automatically started the radio to the bathroom where no one was. No explicit command, no scene, no cube tap. Just 46 seconds after the AI ​​coordinator offered a "relax scene", Italian Classic Hits Sanremo started playing from the empty bathroom.

The bug registered as medium severity (one-shot, can be stopped manually), but the key was that it could happen again with every comfort_suggest. Here is 4 hours of diagnostics condensed into 8 minutes of reading.

Reproduction

  1. The AI coordinator evaluates the situation = comfort_suggest (level 4, evening + idle scene)
  2. TTS reads: "Man, it's evening and nothing is going on. Do you want to start a relax scene?"
  3. User he doesn't answer — neither cube, nor button, nor voice
  4. ~46 s after TTS completed: sh_audio_brain_v2 audio_dispatch event
  5. Speaker bathroom will start playing the radio (even if the user is not in the bathroom)

State when there is a bug

sh_audio_current_mode = 'radio_bathroom'
sh_audio_active_speaker = 'Speaker koupelna'
sh_audio_playing = 'yes'
sh_audio_request = 'idle'           ← nikdo nepožádal o radio
sh_audio_final_request = 'idle'     ← ditto
sh_scene_active = 'idle'            ← scéna se neaktivovala
sh_user_intent = 'idle'             ← user neodpověděl
sh_user_intent_request = 'idle'     ← ditto
sh_ai_coord_last_action = 'comfort_suggest'  ← byla jen NABÍDKA
sh_audio_prev_mode = 'idle'         ← žádné prev radio (nebylo co resumovat)
sh_audio_prev_speaker = ''          ← ditto
sh_tts_resume_pending = 'idle'      ← resume nečeká
sh_tts_resume_target = 'idle'       ← ditto

Key Red Alert: sh_audio_current_mode='radio_bathroom' but sh_audio_prev_mode='idle'. Mode got stuck from the morning routine, no one reset it, and after TTS completion fallback logic used it as "where to fall back to".

Hypotheses that didn't work

H1 — audio_brain auto-execute on comfort_suggest. Hypothesis: the brain may auto-activate the "comfort scene" 30-60 seconds after the suggestion without waiting for a user response. Verified by reading sh_audio_brain_v2 — there is no such handler. Falsified.

H3 — sh_audio_active_speaker stuck from morning. Hypothesis: he stayed from his morning routine active_speaker='Speaker koupelna', audio_brain dispatch routes according to him. Partially true (active_speaker WAS stuck), but dispatch was not the problem — the problem was in the resume_exec fallback logic.

H4 — flow listener on ai_coord_last_action. Hypothesis: somewhere flow has a trigger "sh_ai_coord_last_action changed + condition comfort_suggest → action play radio". Grep across all flows found no such. Falsified.

Root cause (H2 winner)

sh_tts_resume_exec_v1 (id 009149d9-0e49-4881-b41d-502b52ca652c), which is called automatically after each TTS completion, had a fallback handler: 

// BEFORE v1.8
if (target === 'idle' && currentMode === 'radio_bathroom') {
  // Resume bathroom radio
  await dispatchAudio({mode: 'radio_bathroom', speaker: 'Speaker koupelna'});
}

The logic was: "if TTS ended, there was no explicit resume target, and the current mode says bathroom radio, return to bathroom radio". Intention: after a short TTS notification during the shower to summarize the radio that was playing.

What fallback didn't check: if bathroom radio actually played BEFORE TTS. sh_audio_current_mode got stuck on 'radio_bathroom' from the morning routine at 03:35 and no one reset it. At 20:45, the situation was still valid, even though the speaker had been silent for a long time.

Fix v1.8 — prev_playing guard

// AFTER v1.8
if (target === 'idle' && currentMode === 'radio_bathroom') {
  if (sh_audio_prev_playing !== 'yes') {
    logEvent({event: 'tts_resume_skip_no_prev_playing'});
    return;
  }
  // Resume bathroom radio
  await dispatchAudio({mode: 'radio_bathroom', speaker: 'Speaker koupelna'});
}

Additional condition: sh_audio_prev_playing === 'yes'. This variable is set to 'yes' only if the TTS orchestrator detects active audio playback BEFORE it starts. If nothing was playing (just TTS), prev_playing remains 'no' and the resume is not executed.

Test (25.4. night)

After deploying v1.8, I manually reproduced the bug conditions:

  • Reset all audio state vars to clean
  • Setup: sh_audio_current_mode='radio_bathroom', sh_audio_prev_playing='no' (key difference)
  • Trigger TTS via sh_tts_orchestrator_v1
  • Wait 60 sec
  • check: sh_audio_request still 'idle', no dispatch event

Test passed. Resume_exec correctly skipped, no radio fired. Log entry tts_resume_skip_no_prev_playing recorded.

Long-term watch

Fix v1.8 addresses the symptom, not the cause of the stuck sh_audio_current_mode. If we see stuck mode again, we will need to add a reset to the bathroom radio stop logic — when speaker stop, set mode='idle'. Currently, the mode holds its last value, which is basically a dirty state.

Backlog item: tools/audit_audio_state_consistency.py — periodic check if current_mode corresponds to the real speaker_playing state. Brain Guardian extension.

What was learned

The fallback logic must explicitly verify that the condition the fallback responds to is current, ne jen recently. State variables can get stuck in ghost values ​​that look valid but don't match the real world.

This is not the first ghost state bug. Stuck sh_priority_active='tts' the incident was similar — the variable held the value from the incomplete pipeline and blocked subsequent operations. Brain Guardian validator layer (V1 LIVE from 26.4.) is the answer to this whole category of bugs — periodic cross-check state vs. reality.

4 hours of diagnostics → 4 lines of code. A typical ratio for state-driven bugs. Hypothesis ladder (H1 → H2 → H3 → H4) is necessary — without systematic elimination, I would end up with a quick fix that would only mask the symptom.
