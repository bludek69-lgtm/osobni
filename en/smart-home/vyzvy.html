📖 Story · Challenges

What the system has to contend with

What went wrong when building a household and how I looked for a solution. From device limitations to automation error states. These are experiences from my system, not a ready-made guide for every apartment.

Technical details

Smart home in the real world is not "set and forget". Here's a list of real-world problems I've solved — and that you'll have to solve too, once you get past the "few smart lightbulbs" level.

Zigbee battery devices & deep sleep

Battery-powered Zigbee sensors (door/window, motion) go to sleep to save energy. If you wake them up and ask them right away, they will often respond after a few seconds — or not at all. Some older pieces fall into deep sleep, from which the fungi lose their presence (the device looks offline even with a full battery).

A specific incident: Door/Window Sensor SNZB-04 in the dining room. Known firmware bug — periodically falls into an unreachable state even 2 meters from the hub, full battery. Caused a 20 minute delay in arrival response on April 23rd (cleaner did not turn off when window was opened). Solution: replacement for Aqara P2 (Matter/Thread, more stable firmware). In the meantime — multi-signal fallback (motion in the kitchen as a backup signal).

Re-pair = new UUID = silent fail

When you change the battery or re-install the Zigbee device, Homey will generate new UUID. Flow cards + scripts + device map referencing OLD UUID silently fail — no error in the UI, the automation simply does not respond.

Real case 26.4.: Door/Window Sensor Dining room1 re-pair → 3 flows broken, the cleaner did not turn off when the window was opened. Diagnosis: GET /devices/device/<old_id> → 404. Fix: bulk OLD→NEW swap via PUT of each affected flow. Preventive scanner find_orphan_device_refs.py in the backlog.

SIGABRT — Homey kills the script without explanation

Homey runtime kills processes when problems are detected (infinite loop, too many parallel scripts, memory leak). He never writes why — the script simply disappears from the exec log. Debugging SIGABRT is pure detective work: isolation, binary search, test.

Classic Trap: setValue() he calls logEvent(), logEvent() he calls setValue() to write to sh_log_payload → infinite recursion → SIGABRT. Rule: setValue() can only call getVar + updateVariable + log. Never logEvent().

setTimeout does not exist (and crashes)

The natural JS reflex for async delay is setTimeout. In the HomeyScript runtime is not available and the call leads to a mysterious crash with no error message — the script simply ceases to exist.

Solution: own wait() function in combination with Promise.race() for HTTP call timeouts. I had to fix this in dozens of scripts — it was systematic, not one-off.

Deleting script = new UUID = broken flows

In Homey I must never delete HomeyScript. Deleting will generate a new UUID, which will break any Flow tabs referencing the script. The only safe editing is in-place: open script, Ctrl+A, paste, Save.

This rule caused one big outage before I figured it out. Cleanup wave scripts (20× DELETE_CANDIDATE) therefore has its own workflow with 48h soak monitoring + canary testing before the actual delete via GitHub Actions.

Audio pipeline race conditions

Audio was the hardest technical nut. Lots of moving parts — priority engine, audio brain, speaker router, TTS orchestrator, Cast Flow, resume logic. Each part had race conditions, each combination of conditions added an edge case.

An example: briefing at 3:20 in the morning. Pipeline: Gemini API (15s timeout) → TTS text → priority 55 > radio 50 → audio brain interrupt radio → Cast TTS → resume radio. Every step could fail. Crashes: setTimeout, Google Cast 200 char limit, priority conflict, resume race condition. Watchdog sh_audio_pipeline_watchdog_v1 monitors stuck status every minute.

Ghost values — variables that lie

sh_audio_request remained at value tts_kitchen_alert overnight. In the morning the radio did not start because the audio brain saw a pending request — variable she claimed a status that no longer held.

The solution resulted in sh_state_validator_v1, which compares the expected and real state. First production detection: priority_active=tts ghost that blocked the audio pipeline from 00:40 until morning. Without a validator, this would repeat indefinitely.

Args[] from Flow are not reliable

Homey Flow can pass an argument to a script via "con l'argomento". But args[] is unreliable — value is sometimes missing, race condition between trigger and script.

Today all mods go through dedicated Homey Logic variables (sh_kitchen_mode, sh_energy_mode), not via args. Flow always: set variable → run script. The script reads from a variable, not from an argument.

Some APIs are simply unavailable

Homey.notifications.createNotification it exists in the documentation, looks functional, but in a HomeyScript context is not available. Result: is not a function. 19 silent errors in a single day in the log before I found this.

Same pattern: castRadio (flow-only), some Homey.scripts calling. Rule: API must empirically verify in the sandbox, don't trust the documentation. Silent failures are the worst category.
