📖 Pillar · Story

How it was created SMART HOME OS

The journey from a single light bulb controlled by an app to connected apartment control. This page captures the successive steps and the shape of the project at the time; the number of devices and automations belong to the described stages.

Technical details

It wasn't a plan. No roadmap document. It started one bulb controlled by the app and gradually grew to 116 scripts, 203 flows and a layered architecture where Brain Guardian oversees other automations.

Here is the story — phase by phase, crisis by crisis.

Engineering journey

7 stages of evolution

No phase has been planned. Each arose as a reaction to the limit of the previous one.

  1. Phase 1 · ~2023

    Beginning — the first automation in the UI

    Manually adding devices in Homey UI. Classic Flow via drag & drop. "When motion → turn on the light." No architecture, no states. Works for a few minutes, then stops scaling — more Flow than I remember, no oversight.

  2. Phase 2 · script-first transition

    Logic to scripts — not to Flow

    Key decisions: the logic belongs to the HomeyScript script, not to the Flow cards. Flows become just triggers — the script is the "brain". The first generation was born sh_* scripts: sh_morning_brain, sh_light_router, sh_audio_brain. Suddenly it's versionable, readable, debuggable.

  3. Phase 3 · request architecture

    Routers and request piping

    The house became more complex — more zones, more sensors, more lights. Key insight: separate "what is to happen" from "how to do it". Request variables were created (sh_light_request, sh_audio_request) and the routers that interpret them. The morning routine no longer writes directly to the light bulb — it sends a request, the router decides based on phase + sleep + presence + lux.

  4. Phase 4 · self-healing + diagnostics

    When the system recognizes that it has a problem

    Collection of events to Google Sheets via Apps Script WebApp. The diagnostic scripts were created: sh_diag_analyzer, sh_self_healing_v4, sh_audio_pipeline_watchdog. Watchdog detects stuck states, self-healing resets them. Memory_watchdog on GitHub Actions restarts HomeyScript app at ≥125 MB. The system stopped requiring user assistance for common malfunctions.

  5. Phase 5 · Dashboard V7

    UI layer — one system, three screens

    Sidebar nav, multi-zone tiles, V5 KPI cards, status chips, drag/drop layout editor. Three variants: 1024x600 RPi kiosk, 1920x1080 notebook, 2880x1800 monitor. One HTML file + responsive CSS layer. Edit mode allows user to move tiles + save layout to localStorage.

  6. Phase 6 · AI integration

    Gemini as a runtime AI layer

    Briefing (TTS via Cast), comfort suggestion, anomaly detection. Gemini reads the event log, suggests actions, generates morning reports. From reactive automation to proactive assistance. AI does not interfere with management — it is an advisor + observer layer.

  7. Stage 7 · Brain Guardian

    Supervisor over the entire system

    Top-level supervisor — sh_expected_state_engine defines what should be sh_state_validator compares with reality sh_brain_guardian orchestrates sh_release_guard monitors deployments. Score 92/100, validator 100, drift detection live. Detected real bugs — Bug E priority engine ghost, Bedroom TRV missing, morning routine motion vs alarm asymmetry.

Lessons learnt

What the system taught me

Each of these things originally had a simple solution in mind. Then it turned out that it doesn't work that way.

👻 Ghost values

The variable remains stuck in a non-idle state because one step of the pipeline crashed. sh_priority_active='tts' Blocked lights/audio for 14 days. Fix: timestamp + auto-reset always > 60s.

⚡ Audio race conditions

The TTS request comes before the previous track finishes. sh_audio_current_mode overwritten in the wrong order. Fix: pipeline watchdog that monitors not the mode, but the request flow.

🔁 Conflict prevention

Two flows are fighting over the same bulb. Without engine priority, it will appear as flashing. Fix: hierarchy priorities (tts=100, light=60, audio=40) + arbitration.

🪝 Silent fail orphan refs

After re-pairing the device will get a new UUID. Flow trigger of cards referencing old ID = silent fail, no error in UI. Fix: bulk find_orphan_device_refs scanner after each pair.

🧠 Why Brain Guardian was created

Watchdog solves only one specific failure mode. Self-healing is reactive. Brain Guardian = a layer that knows what the system should look like and compares it to what it actually does. Detects drift before the user.

🎯 REUSE FIRST

Tendency to create new entities instead of modifying existing ones. It leads to a chaos of duplicates. Rule: every new thing passes the "is there anything like it?" test. — 9× out of 10 yes, refactor.

What makes the system unique?

4 characteristics that hold together

It is not a "smart home" product checklist. It's the way the system thinks.

Script-first automation

Logic in HomeyScript scripts, Flow as mere triggers. Versionable, debuggable, refactorable. No drag-and-drop chaos.

Self-Healing logic

Stuck states detected by watchdogs, automatic resets, app restart in case of memory leak. The system runs even if something breaks.

AI-assisted diagnostics

Gemini reads the event log and suggests what could be wrong. Brain Guardian validates expected vs actual. Anomaly detection without ML model — only rules and state machine.

Living Operating System

A house is not a finished product — it is a continuously evolving system. Every week a commit, every month a new version of some subsystem. It's not an installation, it's a cultivation.
