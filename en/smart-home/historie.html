📖 Story · History

How the system was created

From the first smart light bulb to the connected home. Each subsequent modification responded to a specific need or problem. Here are the important stages and reasons for the changes.

Technical details

From the first bulb and flow "turn it on when you get home" to an autonomous system that diagnoses and repairs itself. Years of gradual transitions — always from a specific pain point, never from a theory.

  1. Start · Small apartment

    Why a smart home at all?

    An apartment with windows to the street brought a specific problem: aquarium effect. When the light is on in the dining room and the blind is up, passers-by can see inside. The first motivation for automation was not "cool gadgets", but simple privacy protection — privacy interlock between blinds and lights became one of the earliest and most important rules.

  2. Homey Pro 2019 (original generation)

    The first Homey

    Classic flow-based control. Motion → light → timer. Functional, but as the number of devices grew, the logic began to duplicate and collide. The peak was when HW stopped keeping up — dozens of parallel Flow cards and the first HomeyScripts were breaking the runtime. There was a need for more performance and a more open platform.

  3. Transition · Homey Pro 2026

    New generation HW

    Quad-core ARM @ 1.5GHz with 4GB RAM. After the migration I was finally able to run 110+ scripts in parallel no SIGABRT crashes. It opened the way to centralized logic in JavaScript instead of gluing flows. One investment step that unlocked all other architecture.

  4. Refactor · Script-first

    The "logic to the script, not to the flow" rule

    All decision logic moved to sh_* scripts. Flows remain as thin triggers (set variable + run script), nothing more. Routers (open space lighting, shutter, audio, vacuum) and a request-first pipeline were created. Debugging just got a whole lot easier — one place, one file, one clear path.

  5. Multi-signal · REUSE FIRST

    Architectural rules

    No action from one sensor — always 2+ signals. No hardcoded device name — all via Device Map. No new script if an existing one can be extended. The rules are not academic — each arose from a specific incident (morning routine triggered at 3am by a cat, renaming a sensor breaking 20 scripts, …).

  6. Dashboards · multi-resolution

    UI for 3 screens

    Greenfield redesign with premium dark layout. Three variants (1920×1080 notebook, 2880×1800 master monitor, 1024×600 RPi WaveShare 10.1") kiosk sharing the same architecture. V3.7 → V7 cycle completed in two weeks with six iterations.

  7. Live · AI Brain Guardian

    Supervisor layer

    Scripts sh_state_validator, sh_brain_guardian, sh_release_guard, sh_self_healing a sh_gemini_diagnostic it forms a meta-layer that checks the expected state, detects ghost values, blocks deployment of broken changes, and analyzes logs daily via Gemini.
