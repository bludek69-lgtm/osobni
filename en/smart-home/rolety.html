📦 Equipment · Blinds

Blinds with dual role

The blind shades the main room and its position also enters into the rules for light and privacy. Here I show how these functions complement each other and when the blind should be closed.

Technical details

IKEA Fyrtur 1 in the main room — physical shading + privacy signal for the light router. The position is continuous 0–1 (0 = completely down, 1 = completely up), threshold 0.2 = privacy boundary. The safety interlock auto-closes upon light request, which would otherwise reveal the interior.

What does it do?

Roller blind as sensor + actuator

A blind is not just a blackout. The blind is the input for security/privacy decision-making. When the blind is up, you can see directly into the living room from the street. Open lights in that situation = privacy fail. The light router reads the position and blocks.

The position is continuous 0.0-1.0 over capabilities windowcoverings_set (Homey unification). 0 = all the way down, 1 = all the way up. Threshold 0.2 = privacy boundary. Below 0.2 = "closed" for privacy purposes, above 0.2 = "open".

Safety interlock: if the user issues a light request and the blind is above 0.2, light_router will NOT trigger the action directly. Instead: (1) auto-close shutter to 0.15, (2) wait for driver ack, (3) then setCap light. I.e. the blind controls when the lights can go on. v1.13 had inverted comparison → user-closed shutter blocked lights → fix v1.14.

Daily operation

Jak roleta reaguje

Passive most of the day. The action is triggered by time + light request.

  1. In the morning

    Car open

    Schedule slot 06:30 (weekdays) → blind auto-open to 1.0. Target: solar house, user rises into the light. Sleep state already unset (the 3:15 briefing has already taken place).

  2. Day

    Idle / manual

    Roll up, no automatic actions. User can manual rotation (dashboard tile) — setCap windowcoverings_set to a specific value. Plus it reads the position for privacy guard.

  3. Evening

    Privacy interlock

    Darkness outside + presence + shutter > 0.2 + light request → safety interlock. Auto-close shutter at 0.15. After reaching the position (driver ack) it releases light_router and setCap. The user sees a short delay (~5 s) before the blind reaches down.

  4. Night

    Closed

    Schedule slot 22:00 → shutter auto-close to 0.1 (fully). Sleep state active, all lights blocked. The blind holds its position all night.

For the tech-savvy

What's going on under the hood

Privacy comparison, safety interlock, position semantics.

Privacy comparison (why inverted was a bug)

v1.13 had light router code: 

// BEFORE (wrong)
const blindOpen = roletaPos < 0.2;
if (blindOpen && wantsLight) → block;

The logic was: "if blind down (< 0.2) = open space outside → block lights." But that's the other way around — a shutter at 0.1 means down (clouded), not open. Consequence: user-closed blind = blocked lights. The exact opposite of what is required. 

// AFTER (right) v1.14
const blindOpen = roletaPos > 0.2;
if (blindOpen && wantsLight) → block;

Item 0.2 = privacy threshold. Above = open (see inside). Pod = closed (privacy preserved). Memory: reference_open_space_lighting_pipeline.md.

Safety interlock (auto-close pipeline)

When the user emits a light request and the blind is above 0.2 in privacy hours (TOD evening / night, lux below the threshold):

  1. Light_router detects privacy fail
  2. setCap windowcoverings_set = 0.15 (config: sh_cfg_blind_privacy_position)
  3. Listen for driver ack (position reached, ~3–5 s) OR timeout 10 s
  4. After ack: setCap light onoff (original request)
  5. If timeout: log warning + default deny (dark rather than breach)

Pipeline atomically — one flow decides the entire sequence. No race condition ("shutter down + light → during this the user opens the shutter manually" — it should be inside in the 5 s window, but if so, the next cycle will solve it).

Position semantics (windowcoverings_set vs. _state)

Homey has two capabilities:

  • windowcoverings_set: float 0.0–1.0 — target position. Set reads device on drive direction. 0 = bottom (closed), 1 = top (open).
  • windowcoverings_state: enum 'idle' / 'up' / 'down' — current engine state. Read-only from the driver. Useful for "wait for it to finish".

IKEA Fyrtur convention: 0 = full down (rope body coiled), 1 = full up (rope extended). Aqara curtain motor, on the other hand, often 0 = open, 1 = closed — verify per device.

Schedule format (auto-open / auto-close)

Schedule per zone similar to heating: 

{
  "version": 1, "enabled": true,
  "schedule": {
    "weekday": [
      {"time": "06:30", "position": 1.0, "comment": "morning open"},
      {"time": "22:00", "position": 0.1, "comment": "night close"}
    ],
    "weekend": [
      {"time": "08:00", "position": 1.0},
      {"time": "23:00", "position": 0.1}
    ]
  }
}

Cron sh_blind_scheduler_v1 (every 5 min) finds the current slot and applies. Manual override from the dashboard has priority (config: sh_cfg_blind_manual_override_until_ts).

Battery management (Fyrtur ~1 year)

IKEA Fyrtur has an integrated Li-Ion battery, USB-C charging. Capabilities measure_battery:

  • > 50% — green
  • 20-50% — yellow, log warning
  • 10-20% — red, push alert (when implemented)
  • < 10% — critical, charging schedule within a week

Real-life: with 2 cycles per day (open in the morning + close in the evening), the battery lasts ~1 year. Charging takes ~4 hours, can be done overnight without removing. The USB-C cable stays on while charging.
