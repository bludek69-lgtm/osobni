Bug anticiclismo con avviamento a freddo: caldaia bloccata per sempre

La fase A del riscaldamento è entrata in funzione la mattina del 21/4. La caldaia si è accesa, ha funzionato per 5 minuti, si è spenta. Poi non ha più chiuso. EventLog segnalato ogni 2 minuti hold_off_180s_left, dove 180 è stato contato dal tempo trascorso dall'ultima volta e non è stato eseguito lo scorrimento verso il basso.

La protezione anticiclismo era assicurata contro la commutazione rapida della caldaia (protezione contattori). Fondamentalmente ha funzionato, ma ha avuto un caso limite sull'avvio a freddo: dove min_offtime_s mai scaduto. Ecco 4 ore di diagnostica.

Sintomo

La caldaia si è accesa una volta, ha riscaldato il bagno alla temperatura nominale (ca. 5 min), quindi si è spenta secondo l'isteresi. La storia finisce qui: da quel momento in poi non si è più riacceso, anche quando la temperatura è scesa molto al di sotto del valore target.

EventLog dal cron della richiesta ogni 2 minuti: 

06:14:00 demand=on  jidelna=21.0/21.0  koupelna=22.1/22.0  → boiler_request=on
06:16:00 demand=on  ...                                  → boiler_request=on
06:21:00 demand=off jidelna=21.0/21.0  koupelna=22.0/22.0 → boiler_request=off
06:23:00 demand=on  jidelna=20.4/21.0                    → hold_off_180s_left=180
06:25:00 demand=on  jidelna=20.3/21.0                    → hold_off_180s_left=180
06:27:00 demand=on  jidelna=20.2/21.0                    → hold_off_180s_left=180
... (forever)

hold_off_180s_left il conto alla rovescia non è continuato. La caldaia rimase sempre spenta, la sala da pranzo scese lentamente a 21 → 20 → 19 → 18 °C. Senza intervento scenderebbe a 7 °C antigelo (dove il by-pass di sicurezza forzerebbe lo spegnimento della caldaia).

Logica di protezione anticiclismo

sh_heating_demand_v1 v1.1 ha fatto questo controllo: 

// v1.1
const sinceTs = parseInt(await getVar('sh_heating_boiler_since_ts'), 10);
const elapsed = Math.floor((Date.now() - sinceTs) / 1000);
const minOfftimeS = parseInt(await getVar('sh_cfg_heating_min_offtime_s'), 10);

if (boilerState === 'off' && elapsed < minOfftimeS) {
  return {
    request: 'off',
    reason: `hold_off_${minOfftimeS - elapsed}s_left`
  };
}

La logica era: se la caldaia è spenta ed è passato meno di quanto dall'ultimo spegnimento min_offtime_s (default 180 s = 3 min), mantenerlo spento per proteggere il contattore.

Caso limite: avvio a freddo

sh_heating_boiler_since_ts era su una nuova installazione dello script non registrato/non definito. parseInt(undefined) = NaN. Date.now() - NaN = NaN. Math.floor(NaN / 1000) = NaN.

E ora il momento chiave: NaN < 180 in JavaScript valuterà falso. Quindi durante i primi 5 minuti di funzionamento (quando la caldaia si è accesa per la prima volta) c'era un altro ramo e tutto ha funzionato.

Ma dopo la prima transizione di spegnimento (la caldaia si spegne secondo l'isteresi) si è verificato since_ts = 0 qualche logica ombra (rivelato il log di debug: un percorso di esecuzione non è stato impostato correttamente since_ts al momento della transizione e il valore predefinito era 0 dall'inizializzazione). 

// since_ts = 0
elapsed = Math.floor((1697123456000 - 0) / 1000)
       = 1697123456
// 1697123456 < 180 ? FALSE!
// Wait, that's not the bug...

Hmm. 1697123456 < 180 è falso, quindi la guardia NON FALLISCE. Lo script dovrebbe continuare normalmente.

La vera causa principale

Dopo un altro registro di debug, ho scoperto che non c'erano problemi elapsed < minOfftimeS, ma un altro pezzo di codice qui sotto: 

// Safety cutoff
if (sinceTs > 0) {
  // Validation runtime checks
  ...
}

// Anti-cycling check (the actual guard)
if (boilerState === 'off') {
  const safeElapsed = sinceTs > 0 ? elapsed : 0;
  if (safeElapsed < minOfftimeS) {
    return {request: 'off', reason: `hold_off_${minOfftimeS - safeElapsed}s_left`};
  }
}

Ecco la codifica difensiva: if sinceTs era 0 o negativo (errore in init), usa safeElapsed=0 → fall through to guard. 0 < 180 = true → la protezione si chiude → restituisce hold_off.

La logica avrebbe dovuto essere: "se sinceTs non si applica, lasciare chiudere la caldaia (salta protezione)". Invece: "se sinceTs non si applica, trattalo come adesso (più conservatore) → la guardia blocca sempre".

Correggi la versione 1.2

// v1.2 — explicit cold-start escape
if (boilerState === 'off') {
  const safeElapsed = sinceTs > 0
    ? elapsed
    : Number.MAX_SAFE_INTEGER;  // ← cold start: bypass guard
  if (safeElapsed < minOfftimeS) {
    return {request: 'off', reason: `hold_off_${minOfftimeS - safeElapsed}s_left`};
  }
}

Modifica chiave: sinceTs > 0 ? elapsed : Number.MAX_SAFE_INTEGER. Avvio a freddo = fingi che sia trascorso un tempo infinito → la protezione non si blocca mai.

Inoltre risolto il problema in qualsiasi altra parte del codice (altri 3 posti) dove sinceTs > 0 il controllo è stato utilizzato come cancello con un comportamento predefinito errato.

Prova

Ripristina tutte le variabili dello stato di riscaldamento (simulazione dell'avvio a freddo), avvia manualmente il cron della richiesta: 

06:30:00 (cold start) demand=on jidelna=18.0/21.0 → boiler_request=on
06:30:00 since_ts=<set>
06:32:00 demand=on  jidelna=18.5/21.0 → boiler_request=on (still cold)
...
06:45:00 demand=off jidelna=21.0/21.0 → boiler_request=off (target reached)
06:45:00 since_ts=<updated to off transition>
06:47:00 demand=on  jidelna=20.4/21.0 → hold_off_60s_left (legitimately cooling down)
06:48:00 demand=on  jidelna=20.3/21.0 → boiler_request=on (180s elapsed)

Prova superata. L'avviamento a freddo non viene riconosciuto come violazione dell'anticiclismo, il ciclo normale si comporta normalmente dopo la prima disattivazione.

Cosa è stato appreso

La "sicurezza predefinita" spesso non è sicura predefinita. Una codifica difensiva che presuppone il caso peggiore può aggiungere la propria classe di bug: una guardia che "preferisce bloccare anziché rilasciare" può portare alla paralisi del sistema.

Lezioni da questo bug:

  • Caso limite 0/non definito/NaN. Gestione sempre esplicita, non fallthrough implicito tramite coercizione JS. NaN < 180 = false è un trucco in cui mi sono imbattuto.
  • Avviamento a freddo = bypass di sicurezza. All'avvio a freddo, le guardie hanno per definizione "mancanza di dati": il comportamento predefinito dovrebbe essere "lasciare passare al primo avvio", non "bloccare tutto".
  • Tappo di sicurezza per l'ortogonalità. Un'altra guardia di sicurezza (max_runtime_s 4h forzata) non sarebbe d'aiuto in questo caso: la caldaia era spenta, non lui. Le protezioni a più livelli devono coprire tutti i percorsi, non solo quelli sul percorso.
  • EventLog è il mio migliore amico. Senza loghi dettagliati, questo bug sarebbe invisibile: l'interfaccia utente Homey mostra la caldaia spenta, tutto sembra a posto. L'intuizione è arrivata da EventLog grep hold_off_*.

Il bug è stato classificato come "avvio a freddo della macchina a stati", che in genere appare nel software una volta per progetto e poi mai. Qui, invece, la casa, che si ripete ogni mattina, ha un'esposizione costante alla partenza a freddo (dopo ogni interruzione di corrente, dopo ogni implementazione, dopo ogni riavvio di Homey).

Difesa in profondità: sh_brain_guardian_v1 (V1 LIVE dal 26.4.) ha l'invariante “se la caldaia è spenta per sempre + la zona diminuisce lentamente → allerta”. Questo meta livello avrebbe rilevato lo stesso bug entro 15 minuti anche se la correzione v1.2 non fosse esistita.
